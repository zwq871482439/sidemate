## 一、产品目标

当前启动流程存在一个**体感割裂**：用户在「基础服务就绪」阶段（段1）会卡住 10–15 秒（因为 FastAPI 的 `_lifespan` 在 HTTP 监听前同步跑完了 Ollama 启动、模型预热、KB 加载、BatchQueue、TaggingScheduler 等所有重活），而随后的「正在加载模型引擎」阶段（段2）反而只做一个 3 秒的假停留（main.go 第 1078 行注释明说"已经在 HTTP 监听前做完了"），**名不副实**。

本次改造的目标是**让进度条的语义与实际发生的重活对齐**，让用户在每个阶段看到的内容都是真的：

1. **语义对齐**：段1 只做"让 FastAPI 能响应"这一件事（秒级就绪）；段2 真正在后台加载模型引擎，并让前端能感知到加载进度。
2. **降低首感摩擦**：Splash 文案与版式调整，让版本号、阶段描述更清晰、间距更舒展。
3. **概念去技术化**：把"预热/卸载"这种开发者视角的措辞，换成"加载/取消加载"这类用户能懂的词。

> 一句话：**这次改造要解决的，是用户在启动时看到的进度阶段与实际后台工作严重错位带来的"卡在错的阶段"的困惑感。**

## 二、用户故事

**US-1（启动顺畅度）**
作为每天开机就打开桌伴的用户，我希望启动过程中每个阶段都"名副其实"——当进度条显示"正在加载模型引擎"时，模型真的在加载（而不是已经加载完了在假等），这样我看到的等待是可理解的、心理上不焦躁的。

**US-2（启动可预期性）**
作为用户，我希望即使模型没装好、KB 没装好，桌伴的底座也能正常启动并打开网页，让我至少能做基础操作，而不是被启动器的致命错误卡死在 Splash 界面。

**US-3（设置页易用性）**
作为不熟悉技术概念的用户，我希望设置页里的按钮用词是我能看懂的（"加载模型""取消加载"），并且我能自己决定是否在启动时自动加载模型（比如我内存紧张想手动加载）。

## 三、需求池

### P0 — Must have（不做就无法达成核心目标）

#### P0-1 启动流程四段重构（语义对齐）

| 段 | 当前 | 改造后 |
|----|------|--------|
| **段0 环境检查** | GPU 检测 | GPU + 关键依赖检测，**至少 3s** |
| **段1 基础服务就绪** | ❌ 同步阻塞跑完所有重活（10–15s） | ✅ FastAPI **立即监听，不等重活**，**至少 3s** |
| **段2 正在加载模型引擎** | ❌ 假停留 3s（啥都不干） | ✅ **后台跑** Ollama 启动 + 模型预热 + KB 加载，前端轮询 `/api/status` 的 `ready` 字段，**至少 3s**，**若 KB 已安装则需等 KB 也加载完** |
| **段3 守护进程启动** | watchdog，3s | watchdog，**至少 3s**（不变） |

**进度条段位要求**：
- 四段对应 0% / 25% / 50% / 75% / 100%，**均匀分布**
- 总时长**至少 12s**（4 段 × 3s 下限）
- 段内仍可保留"5 小节跳动"的视觉动效（已有实现）

#### P0-2 失败兜底（不阻止底座启动）

- 段2 中任意一项后台任务失败（Ollama 起不来 / 模型预热失败 / KB 加载失败 / 依赖缺失），**跳过失败项，不阻止启动器继续推进**，底座照常启动并打开网页。
- 模型 / KB / 依赖的**异常状态由前端 web 页面以非阻塞方式提示**（如设置页资源面板、对话页顶部 banner），**不在启动器（Splash / 托盘面板）层面阻塞或报致命错误**。
- 仅当 FastAPI 进程本身无法启动（段1 失败）时才视为致命错误——保留现有 3 次自修复重试 + `os.Exit(1)` 兜底逻辑。

#### P0-3 段1 FastAPI 立即监听（消除阻塞根源）

- 当前 `server.py` 的 `_lifespan`（L180–300）在 `yield` 前同步执行了：`ollama_manager.auto_start()` → 模型预热 → `kb.load_models()` → `LLMScheduler` → `TaggingScheduler.start()` → `BatchQueue` 初始化。
- **这些重活必须从 `_lifespan` 的同步阻塞路径移走**，改为在 HTTP 监听后由后台线程/任务执行，使 `waitForServerWithProgress`（main.go L948）的轮询能在秒级命中 200。
- 改造后段1 的职责收窄为：FastAPI 进程拉起 + 路由注册 + 立即监听端口。

#### P0-4 `/api/status` 新增 `ready` 字段（段2 轮询依据）

- 在 `/api/status`（settings_system.py L133）的返回体新增顶层布尔字段 `ready`：
  - `true`：模型预热完成 **且**（若 KB 已安装）KB 模型加载完成。
  - `false`：仍在加载中，或加载失败（失败也属于"本轮加载流程结束"，需区分"加载中"与"加载结束但失败"，建议拆为 `ready` + `load_error` 两个字段，见待确认问题 Q1）。
- Launcher 段2 用 `ready` 字段判断是否可推进到段3；前端 web 页面也可用同一字段决定是否隐藏"模型加载中"提示。

#### P0-5 Splash 版本行拆两行

- 当前版本行（splash_windows.go L498）将名称与版本号拼在一行：
  `verText := "桌伴 · Sidemate · " + ss.version` → 即 "桌伴 · Sidemate · v0.9.5"
- 改为**两行**：
  - 第一行：`桌伴 Sidemate`
  - 第二行：`v0.9.5`（取自 `ss.version`，即 `AppVersion`）
- 两行均居中。

#### P0-6 设置页模型管理按钮改名

| 场景 | 当前文案 | 改造后文案 | 触发条件 |
|------|----------|------------|----------|
| 已安装、未加载 | 预热模型 | **加载模型** | 调用 `/api/warmup`（接口路径不变，仅改前端文案） |
| 已加载 | 卸载模型 | **取消加载** | 调用 `/api/model/unload`（释放内存，GGUF 文件保留） |
| 删除文件 | 删除模型 | **删除模型**（不变） | 删除 GGUF 文件 |

- 改名同时需同步更新 `handleWarmup` / `handleUnload` 内 `btn.textContent` 的回填文案（如失败后恢复按钮文字 "预热模型" → "加载模型"、loading 态 "预热中..." → "加载中..."）。
- `handleUnload` 的二次确认弹窗（settings.js L334）文案"卸载后需要重新预热"需改为"取消加载后需要重新加载才能使用对话功能"。

### P1 — Should have（显著提升体验，但非阻塞核心目标）

#### P1-1 段2 等 KB 加载完成

- 当 KB 扩展已安装（`_kb_installed == True`）时，段2 的 `ready` 必须等到 KB 模型（embedder bge-m3 + reranker）也加载完才置 `true`。
- 当 KB 未安装时，`ready` 只看 LLM 预热结果。
- 这是 P0-4 的细化规则，单独列为 P1 是因为它依赖 KB 加载逻辑的后台化改造（与模型预热同属段2 后台任务）。

#### P1-2 Splash 进度条与阶段描述整体下移

- 将 4 段进度条 + 阶段名（`splashDrawSegmentProgress`，splash_windows.go L609）所在区域**整体下移**。
- 目标视觉关系：**"进度条底 → 窗口底"的垂直距离 ≈ "窗口顶（标题栏底）→ Logo 顶"的垂直距离**，使上下留白对称、整体重心下沉。
- 涉及常量：`baseStepStartY = 200`（splash_windows.go L25）需增大，具体像素值交由架构师/前端定，PRD 只给约束（对称留白）。

#### P1-3 新增配置项 `auto_warmup_llm`

- 在 `config.py` 的 `DEFAULTS` 中新增：
  ```python
  "auto_warmup_llm": True,   # 启动时是否自动加载（预热）LLM 模型
  ```
- `server.py` 的 `_lifespan`（或重构后的后台任务）中，模型预热逻辑用 `if _cfg_get("auto_warmup_llm", True):` 包裹，关闭时跳过 LLM 预热。
- KB 自动加载**保留现状逻辑**（看是否安装，安装就尝试启动），不受 `auto_warmup_llm` 控制——KB 的独立开关留待后续（见 P2-1 / 待确认 Q2）。

#### P1-4 设置页新增"启动时自动加载模型"开关

- 在**模型管理卡片**（index.html L616–634）下方新增一个开关行：
  - **主文案**：「启动时自动加载模型（推荐）」
  - **副文案**：「勾选后启动器会在启动阶段自动加载 LLM，省去首次问答的等待」
- 开关绑定配置项 `auto_warmup_llm`，改动即写入 `settings.json`（复用现有 `config.save()` 机制）。
- 视觉对齐：参考同卡片内"纪要引擎常驻内存"开关（index.html L641–645）的 label + checkbox + 副文案三件套样式。

## 六、待确认问题

**Q1：段2 的 `ready` 字段如何区分"加载中"与"加载结束但失败"？**
当前 `/api/status` 只有模型 `loaded` 状态，没有"加载流程整体是否结束"的信号。若 Ollama 起不来，`ready` 永远是 `false`，段2 会一直等待直到超时。
建议方案：新增两个字段——`ready: bool`（加载流程已结束，无论成败）+ `load_error: str|None`（失败原因，成功时为 null）。Launcher 段2 以 `ready==true` 为推进条件，`load_error` 非空时记日志但不阻塞（符合 P0-2 兜底）。**请架构师确认字段设计。**

**Q2：段2 的等待上限是多少？**
用户要求段2"至少 3s"且"等 KB 也加载完"。若用户机器很慢（KB bge-m3 + reranker 加载需 20s+），段2 会一直停在那里。是否需要一个硬超时（如 60s）后强制推进？**建议设 60s 上限，超时即推进并记 load_error。**

**Q3：Go 侧已启动 Ollama 进程，Python `_lifespan` 又调 `auto_start()`，改造后是否去重？**
main.go L777–782 已在段1 启动 Ollama 进程（`ollama serve`），而 server.py L202–209 的 `ollama_manager.auto_start()` 又会尝试启动。当前靠"已运行就跳过"避免冲突。改造后段2 后台任务是否还需要 `auto_start()`，还是只保留 warmup + KB 加载？**请架构师确认去重策略。**

**Q4：`auto_warmup_llm=false` 时，段2 的 `ready` 何时置 true？**
若用户关闭自动加载，段2 不预热 LLM。此时 `ready` 是否立即置 true（因为"没有需要加载的 LLM 任务"），还是仍需等 KB？按 P1-1 规则，KB 安装则等 KB，否则立即 ready。**请确认此理解。**

## 七、验收标准（摘要）

- [ ] 启动总时长 ≥ 12s，四段进度均匀 0/25/50/75/100%。
- [ ] 段1 在秒级完成（FastAPI 立即监听，不再卡 10–15s）。
- [ ] 段2 进度条推进与后台真实加载进度联动，不再是无意义假停留。
- [ ] 拔掉/破坏模型文件后启动，底座仍能启动并打开网页，前端有非阻塞提示。
- [ ] Splash 版本号显示为两行，进度条上下留白对称。
- [ ] 设置页按钮文案为"加载模型""取消加载""删除模型"。
- [ ] "启动时自动加载模型"开关存在，关闭后下次启动不预热 LLM。
