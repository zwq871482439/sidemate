## 五、P0-1 云端 AI 模式 — 专项设计

### 5.1 需求背景

部分用户场景下本地模型算力不足或模型能力有限（如 Qwen3.5-4B 在复杂任务上表现不佳），需要支持接入云端 OpenAI 兼容 API，同时保留本地模式作为默认/离线选项。

### 5.2 用户体验设计

#### 顶部状态栏切换

```
┌─────────────────────────────────────────────────┐
│ [🟢 正在使用本地AI模型 ▾]  数据不上网 模型跑本地    │   ← 本地模式（默认，绿色 tag）
│ [🔴 正在使用云端AI模型 ▾]  核心数据本地存储         │   ← 在线模式（红色 tag，醒目区分）
└─────────────────────────────────────────────────┘
```

- **点击状态文字**：弹出下拉选择「本地 AI 模型」/「云端 AI 模型」
- **本地模式文案**：「正在使用本地AI模型」+ 绿色 tag + 副标题「数据不上网 模型跑本地」（灰色）
- **在线模式文案**：「正在使用云端AI模型」+ 红色 tag + 副标题「核心数据本地存储」（灰色）
- **切换确认框**：选择后弹出确认弹窗（非 toast），用户手动确认后才切换：
  - 切到云端：「切换到云端 AI 模式后，所有 AI 请求将通过互联网发送到云端服务。确认切换？」[确认] [取消]
  - 切到本地：「切换到本地 AI 模式后，将使用本地运行的模型，无需网络。确认切换？」[确认] [取消]
- 切换完成后 toast 提示：「已切换到云端/本地 AI 模型」

#### 设置 Tab 新增折叠区

设置页底部新增「云端 AI 模型配置」折叠面板（默认折叠）：

```
▼ 云端 AI 模型配置
  API 地址：[_________________________]  （默认 https://api.openai.com/v1）
  API Key： [•••••••••••••••••••••••]  [显示/隐藏]
  模型名称：[_________________________]  （默认 gpt-4o-mini）
  [测试连接]  [保存配置]
```

- 配置信息存储在 `settings.json` 中（加密存储 API Key）
- 首次切换到在线模式时，如果未配置则弹出引导提示跳转设置页

### 5.3 技术方案

#### 技术选型：openai 官方 Python SDK

使用 `openai` 官方库（MIT 协议，基于 httpx），天然支持自定义 `base_url`：

```python
from openai import OpenAI
client = OpenAI(base_url="https://your-api.com/v1", api_key="sk-xxx")
```

优势：
- 官方维护，API 兼容性有保障
- 已内置流式 SSE 支持（`client.chat.completions.create(stream=True)`）
- 所有 OpenAI 兼容服务（DeepSeek、通义千问、Groq、Together AI、Ollama 本身等）均可直接对接
- 无需造轮子

#### 架构设计：双引擎抽象层

```
                    ┌──────────────────┐
                    │  ModelManager    │
                    │  (公共接口层)      │
                    └────────┬─────────┘
                             │
                    ┌────────▼─────────┐
                    │  Engine Router   │  ← 根据 settings 选择引擎
                    └───┬──────────┬───┘
                        │          │
              ┌─────────▼───┐  ┌──▼────────────┐
              │ OllamaEngine│  │ CloudEngine    │
              │ (现有逻辑)   │  │ (openai SDK)  │
              └─────────────┘  └───────────────┘
                   httpx             openai
                     │                  │
                  Ollama          OpenAI API
                 (本地)         (云端/兼容)
```

**核心原则**：所有上层调用（20 个调用点）仍然通过 `ModelManager.chat()` / `ModelManager.chat_stream()` 走统一接口，ModelManager 内部根据当前模式路由到对应引擎。

### 5.4 模型调用点审计（20 处全部需适配）

所有调用均经过 `ModelManager`，统一路由，**无需逐个修改上层调用点**：

| 模块 | 调用点 | 方法 | 数量 |
|------|--------|------|------|
| Chat 对话 | 主对话、think续写、自动续写 | `chat_stream()` | 3 |
| Chat Doc Action | Phase1 提纲、Phase2 正文 | `chat_stream()` | 2 |
| Chat QA Tab | 文件问答 | `chat()` | 1 |
| KB 问答 | SSE 端点 + 内部方法 | `chat_stream()` | 2 |
| KB Chunking | 逐段处理、记忆压缩、最终聚合 | `chat_stream()` | 3 |
| 纪要纠错 | 短文本、长文本分批 | `chat_stream()` | 2 |
| 纪要生成 | AI 会议纪要 | `chat_stream()` | 1 |
| 上下文压缩 | 离线对话压缩 | `chat_stream()` | 1 |
| 会话缓存 | 长对话自动压缩 | `chat_stream()` (间接) | 1 |
| 设置预热 | 模型加载预热 | `httpx.post("/v1/chat/completions")` | 1 |
| 模型管理 | 卸载/删除/列表/状态 | 管理类 API（仅本地有效） | ~3 |

**注意**：切换到在线模式后：
- ✅ 所有推理调用（chat_stream / chat）走云端，包括纪要纠错、上下文压缩等后台任务——**在线模式全走在线**，不降级
- ✅ 模型管理类 API（卸载/删除/列表/内存查询/预热）仍走本地 Ollama，与云端模式**并行不互斥**，用户可随时管理本地模型
- ⚠️ 在线模式后台任务（KB chunking、纪要纠错、上下文压缩）会消耗云端 API 额度，费用由用户承担

### 5.7 边界条件

| 场景 | 处理策略 |
|------|---------|
| 云端 API 不可用（网络断开/Key 失效） | toast 提示错误，不自动回退本地（用户手动切回） |
| 云端模式重启 Launcher | Ollama 仍启动（备用），但不预热模型 |
| 云端模式下用 KB/纪要 | 全走云端推理（后台任务也走云端），费用由用户承担 |

| 首次使用未配置 | 切换到在线模式时弹 toast：「请先在设置中配置云端 AI 模型」|

## 六、P0-2 Research Action（联网研究）— 专项设计

### 6.1 需求背景

在线模式下用户希望能联网查资料并多轮深挖。本质需求不是真正的 agentic loop（沙箱/工具链/代码执行），而是 **搜索增强对话**——模型自主决定何时搜索、搜什么，然后基于搜索结果回答，用户追问时继续。

在线模型普遍支持 200K 上下文，可以承载大量搜索结果和历史对话。

### 6.2 前置条件

- **仅在线模式可见**：前端 action_mode 切换时，`research` 选项仅在云端模式下显示
- **依赖云端 AI 模式（P0-1）**：Research Action 必须在云端引擎就绪后才能使用
- 离线模式下 action_mode 选择器只有 `chat` / `doc`，无 `research`

### 6.3 用户体验设计

#### 入口

在线模式下，顶部 action_mode 下拉新增「研究」选项：
```
┌───────────────────────────────┐
│ 💬 对话  │  📄 文档  │  🔍 研究  │   ← 在线模式时三个选项（slow:kb扩展的kbaction别丢了！！！）
└───────────────────────────────┘
```

#### 交互流程（半自动模式）

```
用户提问：xxx是怎么回事？
                    ↓
┌─ Research Action 半自动循环 ────────────────────────┐
│                                                      │
│  1. 提取搜索关键词 → 调用 Bing 搜索                   │
│  2. 获取搜索结果摘要（标题 + 摘要 + URL）              │
│  3. 拼入 prompt → 送云端模型                          │
│  4. 模型输出回答                                      │
│  5. 如果模型判断信息不足，输出特殊标记：                │
│     <SEARCH:新的搜索关键词>                            │
│     <FETCH:某个URL>                                   │
│  6. 后端检测标记 → 执行搜索/抓取 → 再送模型（同轮续流） │
│  7. 重复 4-6 直到模型不再输出搜索标记（最多 N 轮）      │
│  8. 最终回答末尾带追问建议                              │
│                                                      │
│  SSE 事件流：                                         │
│  event: token    → 正常流式输出（用户可见）            │
│  event: search   → 显示「正在搜索: xxx」（状态提示）   │
│  event: fetch    → 显示「正在阅读: xxx」（状态提示）   │
│  event: done     → 结束，带 stats（搜索次数/抓取次数） │
└──────────────────────────────────────────────────────┘
                    ↓
用户追问 → 继续循环（带上 200K 上下文里的历史搜索结果）
                    ↓
用户满意 → 切回 chat 模式 / 继续研究
```

#### 前端展示

- 搜索/抓取状态用小卡片展示（类似 KB 检索来源卡片）：
  ```
  🔍 搜索了「Python 教程」(Bing) — 8 条结果
  📄 阅读了 3 个网页
  ```
- 回答中引用的来源用 `[1]` `[2]` 标注，末尾列出参考链接（可点击）
- 追问建议以「你可能还想了解：」列表形式展示

### 6.4 搜索引擎选型：Bing(slow：优先选bing.cn!!!)

基于 v0.8 时期测试结论，Bing 搜索 API 最稳定。

| 配置 | 值 |
|------|-----|
| 搜索源 | Bing（bing.com + bing.cn 双源 fallback） |
| API Key | 用户在设置页配置（Microsoft Azure Bing Search API Key）（slow：bing不需要apikey啊，直接用用户本地的模拟开个浏览器去搜不就xing'le |
| 备选方案 | 未来可扩展支持 SearXNG / Tavily（配置化） |

**设置页新增搜索配置折叠区**（仅在在线模式下显示）：

```
▼ 联网搜索配置
  Bing API Key：[••••••••••••••••]  [显示/隐藏]
  搜索区域：    [bing.com ▾]  （bing.com / bing.cn / 双源 fallback）
  [测试搜索]  [保存配置]
```

### 6.5 网页正文抓取策略

采用 **渐进式抓取**：

1. **第一轮搜索**：只返回搜索结果摘要（标题 + snippet + URL），不抓正文
2. **模型判断**：模型根据摘要决定是否需要抓取某个 URL 的正文（输出 `<FETCH:URL>` 标记）
3. **按需抓取**：后端检测到 `<FETCH:URL>` 后，抓取该 URL 的正文（使用 readability 算法提取主要文字内容）
4. **智能截断**：单页面正文最多 10K 字符（超出截断），避免上下文爆炸

优势：
- 大多数情况下搜索摘要足够，省流量省时间
- 模型自己决定要不要深读，效果好
- 避免盲目抓取浪费 token

### 6.6 轮次限制：动态适配

**关键发现**：OpenAI `/v1/models` 接口 **不返回** 上下文窗口大小信息，因此无法动态查询。

**方案：模型能力映射表**

```python
# 在 cloud_engine.py 中维护
MODEL_CAPABILITIES = {
    "gpt-4o": {"context": 128000, "max_output": 16384},
    "gpt-4o-mini": {"context": 128000, "max_output": 16384},
    "gpt-4-turbo": {"context": 128000, "max_output": 4096},
    "gpt-3.5-turbo": {"context": 16385, "max_output": 4096},
    "deepseek-chat": {"context": 65536, "max_output": 8192},
    "deepseek-reasoner": {"context": 65536, "max_output": 8192},
    "qwen-max": {"context": 32768, "max_output": 8192},
    "glm-4": {"context": 128000, "max_output": 4096},
    # ... 更多模型
    "_default": {"context": 32768, "max_output": 4096},  # 未知模型保守值
}
```

- 云端配置时可选择模型，前端显示对应的上下文窗口大小
- Research Action 根据当前模型的 context 动态计算最大搜索轮次：
  ```
  max_search_rounds = min(
    (context_window - estimated_history_tokens) // avg_search_result_tokens,
    10  # 硬上限
  )
  ```
- 同时在设置页云端配置区显示当前模型的上下文窗口信息

### 6.7 上下文管理统一设计

#### 6.7.1 num_ctx 修复（Patch2 必须）

**现状 Bug**：`stream_engine.py` 构建发给 Ollama 的 payload 时只传了 `num_predict`（输出上限），**没传 `num_ctx`**（上下文窗口大小）。Ollama 默认 `num_ctx` 只有 2048-4096，代码以为有 32K 但实际 KV cache 远不够，历史被截断。

**修复**：
```python
# stream_engine.py payload 中新增
"options": {
    "num_predict": max_tokens,
    "num_ctx": 16000,  # ← 新增：显式设置 KV cache 大小
}
```

| 参数 | 修复前 | 修复后 | 说明 |
|------|--------|--------|------|
| `num_ctx` | 未传（Ollama 默认 2K-4K） | **16000** | 16K tokens KV cache |
| `max_history_chars` (4B) | 5000 字符 | **12000 字符** | 16K × 1.5 × 0.5 = 12K |
| `context_window` (4B) | 32000（假值） | **16000**（真实） | 与 num_ctx 对齐 |
| Prefill 耗时（满载） | 不可预测 | ~19 秒 | 16K / 14.2 tok/s |

**为什么 16K 而不是 32K**：16K tokens ≈ 24K 中文字符 ≈ 普通对话 10-15 轮完全够用。32K 满载 prefill 要 37 秒太慢，16K 只要 19 秒可接受。

#### 6.7.3 离线模式：上下文满了强制新建

离线模式（本地 4B 模型）不压缩（4B 压缩质量差、耗时长），采用阈值提示 + 强制新建策略：

```
上下文 > 85%（~13.6K/16K）
    ↓
⚠️ 弹窗提示：「对话接近上限，继续聊天响应会变慢。」
   [新建会话] [继续（可能较慢）]
    ↓
用户选新建 → 自动新建会话（当前会话保留在列表里）
用户选继续 → 放任，圆环变红脉冲
    ↓
上下文 > 95%（~15.2K/16K）
    ↓
🔴 强制新建：系统自动新建会话
   新会话第一条消息插入上一轮对话的简短摘要
```

#### 6.7.4 在线模式：云端模型自动压缩

在线模式用**云端大模型**执行压缩（质量高、速度快），用户发消息时自动触发：

**压缩时机**：方案 A — 发消息时检测超阈值 → 先压缩（有实时进度条） → 再正常推理

```
用户发消息（在线模式）
    ↓
后端检测：历史 > 75% 阈值
    ↓
┌─ 压缩阶段（用云端模型）──────────────────────────────┐
│                                                       │
│  SSE event: compress                                  │
│  {"phase": "preparing", "msg": "正在准备对话历史..."}   │
│                                                       │
│  SSE event: compress                                  │
│  {"phase": "compressing", "progress": 30,             │
│   "msg": "正在压缩对话历史..."}                         │
│  → 后端取对话历史 → 发给云端模型：                      │
│    "请压缩以下对话历史，保留关键信息，输出精简摘要"       │
│                                                       │
│  SSE event: compress                                  │
│  {"phase": "compressing", "progress": 70,             │
│   "msg": "正在压缩对话历史..."}                         │
│  → 云端模型返回压缩结果                                │
│                                                       │
│  SSE event: compress                                  │
│  {"phase": "done", "before": "156K", "after": "44K",  │
│   "msg": "压缩完成 (156K→44K)"}                        │
│  → 替换历史 → 继续正常推理                              │
└───────────────────────────────────────────────────────┘
    ↓
正常推理（压缩后历史 + 用户新消息）
```

**前端实时进度展示**：
- 压缩过程中：圆环区域替换为进度条 + 百分比 + 状态文字
- 压缩完成后：圆环恢复，数值跳变（如 78% → 22%），3 秒后恢复常态
- 全程 SSE 推送，用户实时可见

**为什么不后台静默压缩**：需要锁住消息队列防止压缩中用户发消息导致历史不一致，实现复杂。方案 A 简单可靠，有实时进度条用户不会焦虑，延迟增加 3-5 秒可接受。

#### 6.7.5 上下文参数动态切换总表

切换在线/离线模式时，所有上下文相关参数自动更新：

| 参数 | 离线模式 (Ollama) | 在线模式 (Cloud) | 切换时机 |
|------|-------------------|------------------|---------|
| 上下文窗口 | 16000（num_ctx） | 模型映射表 | 切换时更新 |
| max_tokens (输出) | 4096 (4B profile) | 云端模型限制 | 切换时更新 |
| max_history_chars | 12000 | 200K × 1.5 × 0.5 = 150K | 切换时更新 |
| 压缩策略 | ❌ 不压缩 | ✅ 75% 自动静默压缩 | 模式决定 |
| 超阈值处理 | 弹窗提示 → 95% 强制新建 | 自动静默压缩 → 极端再新建 | 模式决定 |
| UI 圆环 | ◔ xxK/16K | ◔ xxK/200K | 切换时刷新 |

**实现**：`model_manager.py` 的模式切换逻辑调用 `update_context_limits()`，根据当前引擎更新所有参数。前端切换模式后请求 `/api/settings` 刷新圆环。

### 6.11 边界条件

| 场景 | 处理策略 |
|------|---------|
| 搜索 API Key 未配置 | toast 提示「请先在设置中配置 Bing 搜索 API Key」|
| 搜索 API 无响应（网络问题） | 提示搜索失败，模型基于自身知识回答 |
| 网页抓取失败（403/超时/乱码） | 跳过该 URL，只用摘要信息 |
| 搜索结果含不当内容 | 不做过滤，由云端模型自行判断 |
| 模型频繁触发搜索（>10轮） | 硬上限 10 轮搜索 + 10 次抓取，超出后强制结束 |
| 追问时历史搜索结果仍在上下文 | 200K 足够，不做额外清理 |
| 切回离线模式 | research action 不可用，已有对话历史保留 |
