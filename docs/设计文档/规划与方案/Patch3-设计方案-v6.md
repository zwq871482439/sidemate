## 一、三源融合 Agent Prompt（A+C 方案）

### 设计思路

不限制模型"用什么源"，而是告诉模型"你有三个渠道，按需使用，综合回答"。
同时根据 KB 数据控制设置，动态注入一句策略提示。

### Prompt 结构

```
基础 Prompt（A 段）：
  "你拥有三个信息渠道，按需综合使用：
   1. 本地知识库（search_kb）— 用户的私有文档
   2. 互联网搜索（search_web）— 公开信息
   3. 你自身的知识 — 通用知识
   优先使用 search_kb 搜索相关内容。"

动态注入（C 段，按 kb_permission）：
  full:        "知识库标签：合同(12) 季度报告(5) 中医(4) 薪酬(3) ..."
  search-only: （不注入标签，模型只能搜索不能看列表）
  disabled:    （不注入任何 KB 相关提示，不注册 KB 工具）
```

### 涉及文件

| 文件 | 改动 |
|------|------|
| `agent_tools.py` | 更新 `_AGENT_BASE_PROMPT`、`get_tools_and_prompt()` |
| `config.py` | 新增 `DEFAULTS.kb_permission = "full"` |

## 二、KB 数据控制 + 文档打标（方案 I）

### 2.1 KB 权限三档

```
┌──────────────┬───────────────────────────────────────────────────┐
│ full         │ search_kb 可用 + System Prompt 注入 KB 标签概览    │
│              │ 在线默认 search-only，离线默认 full                 │
├──────────────┼───────────────────────────────────────────────────┤
│ search-only  │ 只有 search_kb 可用                               │
│              │ 模型不能看文档列表，但能按关键词检索                 │
│              │ 在线模式默认值（隐私优先）                          │
├──────────────┼───────────────────────────────────────────────────┤
│ disabled     │ 两个工具都不给                                     │
│              │ 纯互联网搜索 + 模型自身知识                         │
└──────────────┴───────────────────────────────────────────────────┘
```

（slow：配置入口：前端设置页，数据发送策略的子选项）。

### 2.2 list_kb_docs → 移除

**最终决定**：从 Agent 工具注册表里**完全移除** `list_kb_docs`。

System Prompt 已注入标签，加上用户问题，大模型有足够信息拼 search_kb 关键词。list_kb_docs 多余。

### 2.3 文档打标（方案 I — 上传时打标）

> **砍掉** 方案δ/方案G（批量采样摘要、Map-Reduce、batch ceiling、复杂断点续传）。
> 摘要目标从"精确蒸馏全文"降级为"给个粗略摘要用于展示"。

#### 生成时机

**异步**，不阻塞上传。上传后 embedding 立即建索引（search_kb 可用），打标在后台排队。

```
上传文档 → embedding 建索引（search_kb 立即可用）→ toast "文档已支持检索，AI标签持续进行中"
         → 打标状态 = pending
         → LLM 有空时异步打标（P2 优先级）
         → 打标完成 → 写入元数据
```

#### 一次 LLM 调用输出

```json
{
  "tags": ["中医", "伤寒论", "方剂", "经典"],
  "summary": "伤寒论学习笔记，涵盖六经辨证体系、主要方剂及应用场景，附个人理解与临床思考。"
}
```

- **tags**（3-5 个关键词）：LLM 自由生成，不做固定分类池选择
- **summary**（~100 字）：LLM 顺便生成，前端"查看文档"按钮展示

#### 输入策略（按文档大小自适应）

| 文档大小 | 输入给 LLM 的内容 | 说明 |
|---------|------------------|------|
| ≤ 3000 字 | 全文 | 直接读 |
| > 3000 字 | 标题层级 + 各章节前 200 字 | 方案γ 零 LLM 提取 |

大文档只需标题+各段首句，4B 模型做关键词提取是强项，一次调用就够。

#### 打标 Prompt

```
"请为以下文档生成3-5个标签关键词和一段100字以内的摘要。
标签应反映文档的核心主题和内容类型，可以是领域词（中医、财务）、
文档类型（报告、合同）、时间词（Q3、2026）或其他关键词。
用逗号分隔标签。

文档标题：伤寒论笔记.docx
文档内容摘要：[标题层级 + 各段首句]

输出格式：
标签：中医, 伤寒论, 方剂, 经典
摘要：伤寒论学习笔记..."
```

#### Tag 聚合 → System Prompt 注入

```python
# 后端自动聚合所有文档的 tags，按频次排序
# 全量注入（无最低频次门槛），硬上限 MAX_TAGS = KB_DOC_LIMIT * 5
tag_counts = {"合同": 12, "季度报告": 5, "中医": 4, "薪酬": 3, ...}

# → "知识库标签：合同(12) 季度报告(5) 中医(4) 薪酬(3) 技术方案(3) ..."
# 0 个文档 → 不注入（KB 为空）
# 1 个文档 → "知识库标签：中医(1) 伤寒论(1) 方剂(1)"
```

**MAX_TAGS 公式**：`KB_DOC_LIMIT * 5`（当前50→250, 未来100→500）

**为什么全量注入**：100文档≈500tag≈2K tokens，在大模型200K上下文里是零头。count=1的tag也有价值——告诉模型"KB里有这类内容"。

#### Tag 归一化

**不做近义词合并、不做全局归一化、不做增量参考。**

每个文档独立自由生成 tag，统计时自然收敛：
- 同类文档自然产生相同短 tag（"中医"而非"中国传统医学"）
- 近义词共存不影响功能（"合同(7)"和"协议(2)"各自有效）
- tag 唯一用途是 System Prompt 注入，帮模型决定"要不要搜 KB"

基础归一化（纯规则，零 LLM 调用）：
```python
def normalize_tag(tag: str) -> str:
    tag = tag.strip()
    tag = tag.replace("，", ",").replace("：", ":").replace("（", "(")
    return tag
```

#### 前端展示

```
上传后：
  ✅ 文档已支持检索
  🏷️ AI标签持续进行中...
  
  用户点"查看文档"按钮：
    done   → 展示 [中医] [伤寒论] [方剂] [经典] + 摘要
    pending → "AI标签完成后显示"
```

#### search_kb Hint 注入

`search_kb` 返回时附带 hint，帮模型判断是否继续搜索：

```json
{
  "chunks": [...],
  "sources": ["Q3报告.docx"],
  "hint": "已从1篇文档中找到相关内容，如需更多可扩大搜索"
}
```

不占工具调用次数，是返回值的一部分。

## 四、Token 计数器精细化

### 4.1 context_window 定义

**核心原则**：环形进度只跟踪**输入 token**（prompt_tokens），输出 token 不挤占输入窗口。

```
┌──────────┬────────────────┬─────────────────────────────────────┐
│ 模式     │ 输入窗口       │ 来源                                │
├──────────┼────────────────┼─────────────────────────────────────┤
│ 在线     │ 模型动态       │ MODEL_CAPABILITIES[name].context    │
│ (GLM-5.1)│ 200K           │ 字典取值                            │
├──────────┼────────────────┼─────────────────────────────────────┤
│ 离线     │ 8K (num_ctx)   │ 固定值（Qwen3.5-4B num_ctx=8192）  │
│ (本地)   │                │ 输入满了 → 提示新建会话              │
└──────────┴────────────────┴─────────────────────────────────────┘

环形进度 = 累计 prompt_tokens / 输入窗口
  - 80% → ⚠️ 即将满
  - 95% → 🔴 触发自动压缩（在线）/ 提示新建会话（离线）
```

### 4.2 数据采集

```
在线模式（CloudEngine SSE 最后一个 chunk）:
  usage.prompt_tokens → 输入 token
  usage.completion_tokens → 输出 token（含 reasoning）
  usage.completion_tokens_details.reasoning_tokens → 推理 token

离线模式（Ollama /api/chat 最终帧）:
  prompt_eval_count → 输入 token
  eval_count → 输出 token
```

### 4.3 数据存储 — chat.json

```json
{
  "role": "assistant",
  "content": "...",
  "timestamp": "2026-06-07T18:36:07",
  "token_stats": {
    "input_tokens": 8523,
    "output_tokens": 421,
    "reasoning_tokens": 3200
  }
}
```

### 4.4 前端展示

```
主显示（环形内）：
  在线：15K / 200K    离线：6K / 8K

hover/tooltip 明细（在线）：
  输入 12.5K | 输出 2.1K | 推理 5.8K | 总消耗 20.4K

hover/tooltip 明细（离线）：
  输入 6.0K / 8K | 输出 2.1K | 输入满 8K 需新建会话
```

### 4.5 涉及文件

| 文件 | 改动 |
|------|------|
| `cloud_engine.py` | 从 SSE 最后 chunk 提取 usage |
| `stream_engine.py` | 从 Ollama 最终帧提取 prompt_eval_count + eval_count |

## 五、LLM 统一调度器

### 5.1 消费者清单与优先级

```
┌──────────────┬──────────────────────┬──────────────┬───────────────┐
│ 消费者       │ 任务描述             │ 使用 LLM？   │ 使用场景      │
├──────────────┼──────────────────────┼──────────────┼───────────────┤
│ P0: Chat     │ 用户实时对话         │ ✅ 生成式    │ 离线走本地    │
│              │ 用户等待，抢占式     │              │ 在线走云端    │
├──────────────┼──────────────────────┼──────────────┼───────────────┤
│ P0: 文库对话 │ 本地KB总结 + 融合    │ ✅ 生成式    │ 永远走本地    │
│              │ 用户主动发起=P0      │              │ 在线/离线都有 │
├──────────────┼──────────────────────┼──────────────┼───────────────┤
│ P0: 纪要     │ 润色 / 纪要总结     │ ✅ 生成式    │ 永远走本地    │
│              │ 用户手动触发=P0      │              │               │
├──────────────┼──────────────────────┼──────────────┼───────────────┤
│ P2: KB打标   │ 文档 tags+summary   │ ✅ 生成式    │ 永远走本地    │
│              │ 后台异步，可被抢占   │              │ 空闲时执行    │
├──────────────┼──────────────────────┼──────────────┼───────────────┤
│ 不走调度器   │ KB检索（嵌入+精排）  │ ❌ 不用LLM   │ bge 模型      │
│              │ 纪要ASR（语音转文字）│ ❌ 不用LLM   │ Whisper       │
│              │ 云端问答（文库对比） │ 走云端API    │ 不占本地LLM   │
└──────────────┴──────────────────────┴──────────────┴───────────────┘
```

### 5.2 调度规则

```
优先级：P0 > P2（所有用户主动发起的都是 P0）
同优先级：FIFO
抢占：P0 之间不抢占（等当前 P0 完成），P2 可被 P0 抢占

在线模式特殊：
  Chat Tab → 云端（不走本地调度器）→ 无冲突
  文库Tab → 本地（P0）
  → 在线模式下 Chat 和文库天然并行，不需要排队

离线模式：
  Chat + 文库 + 纪要 都抢本地 LLM → P0 之间 FIFO 排队

排队 UI（离线模式 / 极端情况）：
  "📚 文库正在生成中，您的请求正在排队  [取消排队]"
  "💬 对话正在生成中，您的请求正在排队  [取消排队]"
```

### 5.3 架构图

```
                    ┌─────────────────────┐
                    │    LLMScheduler      │
                    │  (统一本地LLM调度)    │
                    ├─────────────────────┤
                    │ P0: Chat对话(离线)   │
                    │ P0: 文库本地总结     │ ← KB Tab
                    │ P0: 文库融合总结     │ ← KB Tab（Step2）
                    │ P0: 纪要润色/总结   │
                    │ P2: KB文档打标       │ ← 后台异步
                    └─────────┬───────────┘
                              │
                    ┌─────────┴───────────┐
                    │   CloudEngine API    │ ← 不走调度器
                    │  (独立HTTP通道)       │
                    │  · Chat Tab: Agent   │
                    │  · KB Tab: 直接问答   │
```

## 六、云端AI知识对比（✅ 已定方案）

### 6.1 两个需求分治

```
需求1（Chat Tab，在线模式）：
  目标：有限暴露本地数据，发挥大模型能力
  方式：AgentLoop + search_kb + search_web
        System Prompt 注入 KB 标签概览（有限暴露）
  管道：cloud_pipeline（现有，Patch3 增强）
  特点：大模型主动决策用哪个源

需求2（文库 Tab，在线模式）：
  目标：零暴露本地数据，融合大模型能力
  方式：本地模型搜KB+总结 ∥ 云端模型直接回答 → 本地融合
  管道：compare_pipeline（新建）
  特点：脚本化流程，云端永远看不到本地数据
```

### 6.2 脚本化流程

```
用户在文库Tab提问
  ↓
Step0（Round 2+ 追问时）:
  reformulate(历史摘要 + Q) → Q'          ← 本地LLM补全查询
  成本：~100 tokens in / 50 out，~2秒
  策略：有历史→一定reformulate，无历史→跳过
  效果：追问补全为独立问题，新问题原样返回，不需要区分

Step1: 并行（asyncio）
  ├─ 本地（走调度器 P0）：search_kb(Q或Q') → 精排 → 本地LLM总结
  └─ 云端（独立HTTP）：CloudEngine(question) → 直接回答（不跑AgentLoop）
  ↓
Step2: 两者都 done → 调度器再派发 P0
  └─ 本地LLM融合（本地总结 + 云端回答 → 综合分析）
  ↓
完成
```

**云端不跑 AgentLoop 的原因**：
- 保持"本地私有知识 vs 公开知识"的对比纯粹性
- 速度更快（一次生成 vs 多轮工具调用）
- Token 消耗更低

### 6.3 双线记忆（隐私隔离）

```
🔒 铁律：云端模型永远不能看到本地 KB 的任何内容。

两套独立对话历史：
  memory_local = 融合结果（信息最全，本地安全）
  memory_cloud = 云端自己的回答（纯云端输出，零泄露）

Round 1:
  用户: Q1
  → 本地搜KB→L1, 云端回答→C1, 融合→F1
  → 存储: memory_local=F1, memory_cloud=C1

Round 2 追问:
  用户: Q2
  → 本地上下文: [Q1, F1, Q2]   ← 融合结果（含双路信息）
  → 云端上下文: [Q1, C1, Q2]   ← 只有云端自己说过的话
  → 本地搜KB→L2, 云端回答→C2, 融合→F2
  → 存储: memory_local=F2, memory_cloud=C2

记忆级别 0/1/2 对两条线各自适用。
```

### 6.4 对话记忆自适应（砍掉固定 0/1/2）

```python
# 按 token 预算自动裁剪，从最旧开始
HISTORY_TOKEN_BUDGET = 3000  # 给历史对话的上限

# 8K 总预算审计：
#   system(~300) + chunks(~1500) + 历史(自适应≤3000) + Q + 预留输出(~1500) ≤ 8192
# 效果：短对话(每轮200字)→5-6轮, 长对话(每轮800字)→自动裁剪到2轮
# 对比模式：只存融合结果，不存中间双列输出（纯UI层）
```

**前端移除固定 0/1/2 三档，改为上下文指示器**：

## 十、已砍掉方案

| 方案 | 内容 | 砍掉原因 |
|------|------|---------|
| 方案δ | 批量采样摘要（chunk→batch→per-batch LLM→合并） | 目标不是精确蒸馏，打标足够；复杂度高，收益低 |
| 方案G | 自适应 batch + Map-Reduce + 15-batch ceiling | 同上，被方案I替代 |
| 方案H | 固定分类池(20个) + LLM选择 | 4B做20选1有负担，纯Tag更灵活更简单 |
| list_kb_docs | 文档列表工具 | 标签注入足够，工具多余 |
| 断点续传(打标) | batch级断点续传给打标用 | 打标是单次LLM调用，被抢占就标记pending重跑 |
| 云端AgentLoop | 云端对比模式跑搜索工具 | 保持对比纯粹性 + 速度 + Token 消耗 |
| Tag 全局归一化 | LLM二次处理合并近义词 | 4B处理大量tag不可靠，自然收敛足够 |
| Tag 增量参考 | 打标时参考已有tag列表 | 文档间无关联时干扰4B，独立打标更稳 |
| 固定记忆级别 | 0/1/2 三档手动选择 | 改为自适应裁剪，按token预算自动管理 |
