## 二、Patch 6：本地知识库 + 录音纪要

### 2.0 总体目标

问答Tab从"临时文件问答"升级为**持久化本地知识库**：
- 文件导入后自动分块+向量化索引，支持多文件管理（上限20个文档）
- 问答时基于嵌入模型语义检索相关段落，而非传完整文件
- 新增独立"纪要Tab"：录音→转文字→入库→AI总结的完整链路
- Whisper语音转写作为**可选扩展包**，默认不含，需用户手动导入安装

### 2.2 新增模块

#### (1) `knowledge_base.py` — 知识库核心（新增）

```
职责：文档管理 + 分块索引 + 语义检索 + 问答
存储：data/knowledge_base.json + data/kb_vectors.npy（向量索引）
依赖：sentence-transformers（bge-small-zh-v1.5，~90MB）

数据结构：
{
  "version": 1,
  "documents": [
    {
      "doc_id": "uuid",
      "filename": "报告.pdf",
      "file_type": "pdf",
      "file_size": 1024000,
      "imported_at": "2026-05-19T08:00:00",
      "status": "ready",            // pending/processing/indexing/ready/paused/cancelled/error
      "chunk_count": 12,
      "total_chars": 45000,
      "progress": 1.0,              // 处理进度 0.0-1.0
      "metadata": { "title": "", "author": "", "pages": 15 }
    }
  ],
  "chunks": [
    {
      "chunk_id": "uuid",
      "doc_id": "父文档uuid",
      "index": 0,
      "text": "分块文本内容...",
      "char_count": 2300,
      "heading": "第一章 系统架构"
    }
  ],
  "settings": {
    "max_documents": 20,
    "chunk_max_chars": 2500,
    "chunk_overlap_chars": 200,
    "search_top_k": 5,
    "embedding_model": "bge-small-zh-v1.5"
  }
}

向量索引（kb_vectors.npy）：
  numpy矩阵，shape = (N_chunks, 512)
  每行 = 一个chunk的嵌入向量
```

**核心方法**：
- `import_document(filename, text, file_type, source="upload")` → 解析→分块→生成嵌入→存储（异步）
  - source: "upload"=用户上传 | "transcript"=纪要转写稿入库
- `search(query, top_k=5)` → query嵌入→余弦相似度排序→返回相关chunk列表
- `delete_document(doc_id)` → D30: 删除文档+chunk+对应向量行（释放空间）
- `list_documents()` → 列出所有文档（含来源/状态/大小/块数/进度）
- `ask(question, top_k=5)` → 检索相关chunk→构造prompt→调用模型→返回答案（含来源标注）
- `get_processing_status(doc_id)` → 查询文档处理进度
- `pause_processing(doc_id)` → D32: 暂停文档处理（保留已处理进度）
- `resume_processing(doc_id)` → D32: 恢复文档处理
- `cancel_processing(doc_id)` → D32: 取消处理（清理已处理数据）
- `pause_all_processing()` → D31: 暂停所有知识库处理（录音时让步）
- `resume_all_processing()` → D31: 恢复所有知识库处理（录音结束后）

**资源让步策略（D31）**：
  实时录音转写 = 最高优先级
  知识库文档处理 = 低优先级，录音时自动暂停

  优先级链：
  1. 实时录音转写（Whisper CPU，最高）
  2. 转写纠错（8B NPU）
  3. 知识库嵌入处理（CPU，最低，录音时让步）

  录音开始 → 知识库处理自动暂停
  录音结束 → 知识库处理自动恢复

**大文档处理策略**（支持300-500页）：
- 分块数量上限放宽到1000（原来500）
- 嵌入向量化分批处理：每批50个chunk，避免内存峰值
- 处理过程完全异步，前端轮询进度
- 超大文档（>200个chunk）先做粗分块（章节级），再对相关章节做细检索

**关键设计决策**：
- **为什么用嵌入模型而不是BM25？** 语义检索——用户问"怎么部署"能匹配到"安装命令"段落，关键词检索做不到
- **bge-small-zh-v1.5**：90MB，512维，中文场景表现优秀，sentence-transformers一行加载
- **向量存储用numpy**：500个chunk×512维 = ~1MB，不需要向量数据库，numpy矩阵足够

#### (2) `recorder.py` — 录音纪要核心（新增）

```
职责：录音会话管理 + 音频拼接 + 转写调度
依赖：浏览器MediaRecorder（前端） + Whisper扩展包（可选）

核心方法：
- start_session() → 创建录音会话，返回session_id
- append_chunk(session_id, audio_bytes) → 追加音频块
- finish_session(session_id) → 结束录音，拼接完整音频，触发转写（如有Whisper）
- get_transcript(session_id) → 获取转写结果
- summarize(session_id) → 8B模型生成会议纪要
- import_to_kb(session_id) → 转写稿导入知识库作为一个文档

录音会话数据结构：
{

  - 锁定对话让Whisper+8B专心干活，速度快、质量高

```

- realtime_transcribe(session_id, audio_chunk) → 实时转写单个chunk（D25）

    - Whisper即时转写返回文字
    - 前端滚动展示（延迟~10秒可接受）

    - 拼接完整音频
    - 对完整音频做两阶段转写（粗稿+纠错）
    - 实时转写的片段仅作预览，最终以完整转写为准
- transcribe(session_id) → 两阶段转写（D37: 8B纠错按500-1000字/批次）
- import_audio(file_path) → 导入已有音频文件加入处理队列
- pause_processing(session_id) → 暂停处理（D27）
- resume_processing(session_id) → 恢复处理（D27）
- cancel_processing(session_id) → 取消处理（D27）
- get_transcript(session_id) → 获取最终转写结果（纠错后）
- get_rough_draft(session_id) → 获取粗稿（查看页折叠展示 D23）
- update_transcript(session_id, text) → D38: 用户编辑转写稿（入库前可修改）

- import_to_kb(session_id) → 转写稿导入知识库（D39: 加入独立检索索引，不占KB额度）
- delete_session(session_id) → D34: 删除录音（文件+转写数据+粗稿/最终稿）
- get_storage_usage() → D34: 统计录音占用磁盘空间
- recover_sessions() → D36: 启动时扫描落盘状态，恢复未完成的session
- get_sessions() → 历史录音列表（D39: 最多20个session）

录音会话数据结构（持久化到 data/recordings/sessions.json，D36崩溃恢复）：

  "source": "recording",          // recording=现场录音 | import=导入文件

    → D43: 可暂停/恢复录音（MediaRecorder.pause/resume）
    → 录音期间: 后台处理队列暂停（D26）

  导入文件状态机：

    → 排队中/转写中: 可暂停/取消（D27）
    → 转写中: 对话Tab锁定（D22）

    → transcribing/refining: 根据进度从断点继续
    → 已落盘chunk+进度确保"别崩了白录了"

两种使用模式：
1. 现场录音：MediaRecorder采集 → 实时chunk转写预览 → 停止后完整两阶段转写
2. 导入文件：上传已有音频(mp3/wav/m4a/webm) → 加入处理队列 → 两阶段转写

硬件占用统计（展示给用户，D34）：

  - 释放后显示：已释放 XXX MB
  - 录音空间占用：已使用 XX MB（历史录音总数）

- **实时转写**（D25）：录音中每10秒一个chunk，Whisper逐块转写，前端滚动展示，延迟~10秒

- **录音暂停处理**（D26）：录音期间CPU+NPU全力跑实时转写，后台导入处理暂停，录音结束自动恢复

- **转写锁定**（D22）：转写期间对话Tab禁用，Whisper+8B专心干活，完成后自动解锁

### 2.5 技术风险

| 风险 | 影响 | 缓解策略 |
|------|------|----------|
| bge-small-zh随主程序预装（D33） | 安装包增大约90MB | 可接受，90MB换零配置开箱即用 |
| 500页文档分块>200个，向量化耗时长 | 用户等待 | 完全异步+进度条，不阻塞UI；大文档分批处理(每批50chunk) |
| Whisper medium ZIP包~1.5GB偏大 | 下载/存储压力 | 提供small版(~550MB)作为轻量替代；用户自行权衡 |
| faster-whisper wheels预编译兼容性 | 安装失败 | 提供CPU版通用wheel；严格锁定Python版本 |
| 转写期间锁定对话Tab | 用户体验中断 | 转写前明确提示"对话暂不可用"；显示进度+预计时间；转写完自动解锁 |
| medium模型CPU转写速度 | 长音频转写耗时 | 异步后台+进度条；转写期间让Whisper+8B专心干活 |
| 安装时选错版本想换 | 需要卸载重装 | 明确提示"安装后不可切换"；卸载前确认框 |
| 模型加载5-15秒阻塞体验 | 用户等待 | 异步加载+loading动画；加载后常驻不重复加载 |

### 2.6 不做什么

- 
- ❌ 不做实时语音对话 —— 录音转写已够复杂
- 
- ❌ 不做云端同步 —— 数据不出本机
- ❌ 不把Whisper内置 —— 扩展包形式，用户按需安装

- ❌ 不做单文件临时问答 —— D41：所有文档必须入库后才能问答，取消临时模式

### 3.2 内存预算管理（C线 — 核心功能）

#### 背景问题

当前（Patch 7）16GB 机器上内存占用实测：

当前（Patch 7）16GB 机器上内存占用实测：
```
启动后基础    ~545 MB
加载8B模型    → 6989 MB（+6444 MB）

**三层防护**：

1. **Lazy Reranker 加载**：Reranker 仅在 KB 问答检索时加载，空闲超时后自动卸载（省 ~600MB 常驻）
2. **内存预算硬限制**：新增 `MemoryManager` 类，操作前检查预算，超限则拒绝并提示
3. **INT8 量化预留**（Patch 9+）：OV 模型转 INT8，预计 embedder 594→150MB，reranker 1276→320MB（本 Patch 仅预留接口）

class MemoryManager:
    """内存预算管理器 — 操作前检查，超限拒绝"""
    
    def __init__(self, budget_mb=8000):
        self.budget_mb = budget_mb          # 总预算（默认8GB）
        self.base_mb = 0                    # 基础占用（启动后实测）
        self.modules = {}                   # {module_name: current_mb}
    
    def measure(self) -> int:
        """psutil.Process.rss 实测当前总占用（MB）"""
    
    def can_allocate(self, estimated_mb) -> bool:
        """检查是否有足够预算"""
    
    def register(self, module_name, mb):
        """注册模块占用"""
    
    def unregister(self, module_name):
        """模块卸载，释放占用"""
    
    def get_report(self) -> dict:
        """返回预算报告：总额/已用/可用/各模块明细"""

#### Lazy Reranker 策略

```
KB模块状态（Patch 7 已有三级状态机）：
  未安装(Onboarding) → 已安装未加载(Inactive) → 已加载就绪(Ready)

Patch 8 拆分为更细粒度：
  已加载就绪(Ready) = Embedder常驻 + Reranker懒加载
  
Reranker生命周期：
  1. KB激活时：只加载 Embedder（~800MB）
  2. 用户发起KB问答：触发 Reranker 加载（~600MB）→ 执行检索 → 返回结果

### 3.4 模型调用 Pipeline（E线 — 请求调度）

#### 背景问题

当前（Patch 7）所有 LLM 调用共享一把 `_gen_lock`（非公平 threading.Lock）：

```
调用方                     竞争方式              问题
────────────────────────────────────────────────────────────
用户对话（SSE）           _gen_lock.acquire()   ← 最高优先级，但无特殊待遇
KB 文档摘要（后台）       _gen_lock.acquire()   ← 低优先级，但跟用户抢锁
转写纠错（后台）          _gen_lock.acquire()   ← 低优先级，同上
上下文压缩（后台）        _gen_lock.acquire()   ← 低优先级，同上
摘要重试                  _gen_lock.acquire()   ← 低优先级，同上
```

**典型故障场景**：
1. 用户导入文档 → KB 摘要生成请求拿锁 → 用户发消息等 30 秒超时 → "等待设备释放超时"
2. 多个后台任务排队 → 摘要第 1 次失败 → 等待 5 秒重试 → 期间用户又超时
3. 所有调用方平等竞争 → 后台摘要可能"插队"到用户对话前面

#### 核心思路

**优先级队列 + 取消机制**：

1. **两级优先级**：
   - `HIGH`：用户对话（`chat_stream`、`chat`）、手动触发的操作
   - `LOW`：后台摘要、纠错、压缩、重试

2. **公平调度**：
   - HIGH 请求可以抢占 LOW 请求（LOW 正在执行时，等它完成当前 token 后释放）
   - HIGH 等待时，不再运行的 LOW 请求让出位置
   - LOW 请求之间 FIFO 排队

3. **取消机制**：
   - 用户发新消息时，正在排队的 LOW 请求自动取消（不再需要了）
   - 后台任务被抢占后，重新排入队列尾部（不丢弃）

#### 新增类：`GenerateQueue`

```python
# 放在 models.py 内（或独立 generate_queue.py）
class GenerateQueue:
    """LLM 生成请求队列 — 优先级调度 + 抢占"""

    HIGH = "high"   # 用户对话
    LOW = "low"     # 后台任务

    def __init__(self):
        self._queue = []          # [(priority, seq_num, event, result_holder)]
        self._seq = 0             # FIFO 序号
        self._lock = threading.Lock()
        self._active = None       # 当前执行的请求
        self._active_priority = None

    def submit(self, priority="low", cancel_low_on_high=False):
        """提交生成请求，返回 GenerateTicket"""
        # cancel_low_on_high=True 时，HIGH 到达会取消排队中的 LOW

    def release(self, ticket):
        """生成完成，释放"设备"给下一个请求"""

    def cancel_all_low(self):
        """取消所有排队的 LOW 请求（用户发新消息时调用）"""

    @property
    def queue_length(self) -> int:
        """当前排队数量"""

    @property
    def queue_info(self) -> dict:
        """队列状态报告"""
```

#### 调用方改造

```
调用方                  优先级    改动
─────────────────────────────────────────────
chat_stream()          HIGH      submit(HIGH) + 异常时 cancel_all_low()
chat()                 HIGH      submit(HIGH)
kb._generate_summary() LOW       submit(LOW)
kb.ask() 内部摘要      LOW       submit(LOW) 
recorder._refine()     LOW       submit(LOW)
server._update_cache() LOW       submit(LOW)  （模型压缩时）
```

#### 前端排队提示

当 LLM 正忙、用户请求在排队时：
- SSE 首个事件返回 `{"type": "queue", "position": N, "estimated_wait": "5s"}`
- 前端显示"模型正忙，排队中（第 N 位）..."
- 排到后正常流式输出

| Reranker 懒加载延迟 | KB问答首次响应变慢（2-3秒加载） | 加载动画提示"正在加载检索模块..."；**设置页增加 Reranker 常驻开关**，用户可选 |
| 内存预算判断不准 | psutil RSS 含共享内存映射，实测值虚高 | 保留安全余量（budget × 0.9）；模块级截断上限兜底 |
| 超时卸载 Reranker 后立即又需要 | 频繁加载/卸载降低体验 | 5分钟超时可配；**设置页常驻选项（超时不退出）** |
| 删除 ST/ct2 回退路径 | OV 加载失败时无降级方案 | 重点确保 OV 稳定性；OV pipeline 初始化时增加健壮性检查 + 明确错误提示 |
| 技术债清理引入回归 | 原本工作的功能被意外破坏 | **每项清理后前端手动测试验证**（HTML 文档审阅），不只依赖 API 测试 |
| GenerateQueue 死锁 | 所有 LLM 调用卡死 | **队列内部超时兜底**：submit() 默认 60s 总超时；release() 放 finally；队列维护线程定期检查卡住的请求 |
| HIGH 抢占 LOW 频繁 | 后台摘要反复被取消重排 | LOW 被抢占后重新排队（不丢弃）；最多重排3次后降级为规则摘要 |
| 队列状态与前端不同步 | 排队提示不准确 | SSE queue 事件每次队列变化时推送 |

### 3.7 不做什么

- ❌ 不做在线补课（tutor.py）—— 推迟到 v2.x，8B 模型自我分析能力不足
- ❌ 不做自审压缩（context_compressor v2）—— 推迟到 v2.x，同上
- ❌ 不做 insight 记忆类型 —— 推迟到 v2.x，依赖补课/自审的输出
- ❌ 不做 INT8 量化 —— 本 Patch 仅预留 MemoryManager 接口，量化留给 Patch 9+（**slow 质疑必要性**→ 暂不列入，后续根据实际内存压力再评估）
- ❌ 不删 OV → ST 回退路径 → **根据 slow 审阅意见：删除 ST/ct2 回退路径，重点确保 OV 稳定性**。详见 D线 P8-19 任务
- ❌ 不做多级优先级（>2级）—— HIGH/LOW 足够，更多级别增加复杂度无收益
- ❌ 不做多模型并行 —— 单 NPU 设备，本质是串行
- ❌ 不做请求持久化 —— 重启清空队列，合理
