## 一、已完成工作总结（v0.5.6 → 今）

### Bug 修复：空思考标签三重异常 ✅

**问题**：Qwen3-8B 有时输出 `<think\n</think\n`（开始/结束标签间无内容），导致三个连锁 bug：
1. think 字段为空 → 折叠区无内容
2. content 前缀 `<think\n` 被 HTML 渲染器吞掉 → 用户看到英文开头
3. chars=8 → 统计严重失真

**修复**（3 处）：`models.py` 移除 `if think_content:` 条件 → 始终 yield fold；`server.py` 统计加防御

### Bug 修复：中文提问英文回答 ✅

**根因**：system prompt 规则 2"绝不使用中文"被模型泛化
**修复**：`models.py` 规则 2 加括号限定"(仅限代码，其他内容正常用中文)"

### Bug 修复：中断后模型不响应 ✅

**根因**：前端中断后 push 空 assistant 消息到 `currentMessages`，污染后续 history
**修复**：前端空内容不 push；后端空回复不保存；入口重置 `_stop_generation`

### 任务 2：智能任务分类器（核心功能）

#### 2.1 分类算法（加权关键词评分）

**设计决策**：采用加权关键词评分而非 LLM/BERT 分类（零延迟、零额外 token、~80% 准确率覆盖日常办公场景）

```python
# task_classifier.py — 纯函数，无类、无依赖

REASONING_KEYWORDS = {
    # 数学运算
    "计算": 3, "算": 2, "方程": 4, "求解": 3, "等于": 2, "多少": 2,
    "概率": 4, "证明": 4, "推导": 3, "积分": 4, "微分": 4,
    # 逻辑推理
    "为什么": 3, "分析": 2, "原因": 2, "逻辑": 3, "推理": 4,
    # 经典题型信号
    "水池": 4, "鸡兔": 4, "速度": 3, "路程": 3, "小时": 2,
    # 数字+运算符组合
    r"\d+.*[\+\-\*/×÷].*\d+": 5,
}

CODE_KEYWORDS = {
    "代码": 3, "函数": 3, "class": 3, "def": 3, "import": 2,
    "bug": 4, "报错": 4, "debug": 4, "重构": 3, "优化": 2,
    "写.*程序": 4, "写.*脚本": 4, "写.*函数": 4,
    "```": 3, "python": 2, "javascript": 2, "代码块": 2,
}

TEXT_KEYWORDS = {
    "翻译": 4, "translate": 3, "英文": 2, "中文": 2,
    "摘要": 4, "总结": 3, "概括": 3,
    "改写": 4, "润色": 3, "重写": 3,
    "列表": 2, "todo": 3, "待办": 3, "清单": 3,
    "格式": 2, "模板": 2, "信函": 3,
}
```

**分类逻辑**：
1. 对消息做三类关键词匹配，分别计算总分
2. 同时扫描最近 1-2 条 assistant 历史，如果包含 ` ``` ` 则 code 类 +2 继承分
3. 取最高分类；若三类分数均 ≤ 1，默认 code（覆盖面最广的办公场景）
4. 返回 `(task_type, confidence)` 元组

#### 2.2 三档思考策略

| 任务类型 | 思考控制 | temperature | 注入位置 | 效果 |
|----------|----------|-------------|----------|------|
| reasoning | 不限制（full think） | 0.6 | — | 保持原有行为 |
| code | "思考控制在30字以内" | 0.5 | system prompt 规则区 | 思考从 1348→~50 字，速度 +40% |
| text | `/no_think` | 0.4 | system prompt 末尾 | 无 `<think/>` 输出，速度 +78% |

**Qwen3 思考控制**：原生支持 `/no_think` 指令，system prompt 或消息末尾追加即可关闭思考。

#### 2.3 后端集成

- **`task_classifier.py`**（新增）：纯函数 `classify_task(message, history)` → `(task_type, confidence)`
- **`models.py`** `_build_prompt()` 集成：
  1. 调用 `classify_task()` 获取分类
  2. 根据分类注入对应思考控制指令
  3. 微调 temperature
  4. 返回分类结果供 SSE 透传
- **`server.py`** SSE 新增 `task_type` 事件类型，发送给前端

#### 2.4 前端展示（用户已确认方案）

**核心设计**：可点击的 chip 标签，不是独立 Tab

1. **对话区域 chip 展示**：
   - 每条 assistant 消息的统计标签区域，新增任务类型 chip
   - 样式：小药丸标签，颜色区分（reasoning=蓝、code=绿、text=橙）
   - **可点击**：点击 chip 弹出覆盖面板（popover），可手动切换分类并重新生成

2. **覆盖面板（Popover）内容**：
   - 当前分类 + 置信度
   - 三个分类按钮（reasoning / code / text），点击即切换
   - 切换后自动重新生成该条回复（用新的思考策略）
   - 不加独立 Tab，保持 UI 简洁

3. **状态栏联动**：
   - 底部状态栏显示最近一次的任务类型标签

**前端改动文件**：`index.html`（~80 行新增）

### 任务 3：话题漂移检测 + 新 Session 建议

**用户痛点**：用户不知道要新建对话，在同一 session 里聊多个不相关话题，导致上下文污染、模型回复质量下降。

#### 3.1 检测机制（B+C 组合方案，用户已确认）

**触发条件**（满足任一即提示）：

| 条件 | 阈值 | 说明 |
|------|------|------|
| **B. 话题漂移** | 关键词重叠度 < 30% | 当前消息与最近 3 条消息的关键词集合重合率低于阈值 |
| **C. Session 膨胀** | 消息数 > `max_rounds * 2` | 动态跟随模型 profile（8B=12条、4B=12条、1.5B=10条） |
| **时间间隔** | > 30 分钟 | 距离上一条消息超过 30 分钟（辅助信号，不单独触发） |

**组合逻辑**：
- 时间 > 30 分钟 **且** 漂移 → 提示（新话题开始）
- 膨胀超限 → 提示（session 太长）
- 仅漂移但时间连续 → 不提示（可能是深入讨论的转折）
- 仅时间间隔但话题连续 → 不提示

#### 3.2 关键词提取（轻量级）

- 中文：jieba 分词取 top-5 实词（或简单按字符 bigram）
- 英文：空格分词取 top-5（去掉停用词）
- 实现位置：`task_classifier.py` 新增 `extract_keywords(text)` 函数
- 不引入额外依赖，纯规则实现

#### 3.3 前端交互

- 检测到新话题时，聊天区域顶部出现**非侵入式提示条**：
  ```
  🔄 检测到新话题，建议新建对话  [新建对话] [继续当前]
  ```
- 用户可选择：
  - "新建对话" → 自动创建新 session，当前消息移入新 session
  - "继续当前" → 关闭提示条，继续在当前 session 聊（不影响用户流程）
- 提示条**不阻断输入**，用户可以忽略它直接继续打字

#### 3.4 Session 膨胀阈值（动态计算）

```python
# 根据 _MODEL_PROFILES 动态计算
profile = _MODEL_PROFILES.get(model_size, _MODEL_PROFILES[8])
swell_threshold = profile["max_rounds"] * 2  # 8B=12, 4B=12, 1.5B=10
```

- `server.py`：SSE 新增 `topic_drift` 事件
- `index.html`：新增提示条 UI + 交互逻辑

#### 5.2 NPU/GPU 模式切换

**需求**：用户可选择用 NPU 还是 GPU 跑本地模型，不必重启服务。

**现有代码基础**（`models.py`）：
- `_detect_device()` (L121)：启动时自动检测设备，优先级 NPU > GPU > CPU
- `_default_device` (L56)：全局默认设备
- `load()` (L360)：`genai.LLMPipeline(cfg["path"], device=cfg["device"])`
- 每个模型配置有 `device` 字段 (L185)

**实现方案**：

1. **后端 `models.py`**：
   - 新增 `switch_device(new_device)` 方法：
     - 校验 `new_device` 在 OpenVINO 可用设备列表中
     - 更新 `_default_device`
     - 如果当前有已加载的 LLM → 卸载并提示用户重新加载（因为 `LLMPipeline` 的 device 在创建时指定，不可热切换）
   - 新增 `get_available_devices()` 方法：返回 OpenVINO 检测到的设备列表

2. **后端 `server.py`**：
   - 新增 `POST /api/device/switch`：接收 `{"device": "NPU"|"GPU"|"CPU"}`，调用 `switch_device()`
   - 新增 `GET /api/devices`：返回可用设备列表 + 当前选中设备
   - 切换设备后，如果已加载模型 → 自动卸载（NPU/GPU 显存互斥）

3. **前端 `index.html`**：
   - 设置页新增设备选择区域：
     - 下拉菜单列出可用设备（NPU/GPU/CPU），当前设备高亮
     - 不可用的设备灰色禁用（如没有 NPU 就不可选）
     - 切换时确认提示："切换设备将卸载当前模型，是否继续？"
   - 状态栏设备标签联动更新（已有的"NPU模式"/"GPU模式"标签）

4. **设备切换流程**：
   ```
   用户选择设备 → 确认弹窗 → 调用 /api/device/switch
     → 后端校验设备可用
     → 卸载当前模型
     → 更新 _default_device
     → 返回成功
     → 前端刷新状态（模型列表清空，设备标签更新）
     → 用户手动重新加载模型（在新设备上）
   ```

**涉及文件**：
| 文件 | 变更 |
|------|------|
| `models.py` | 新增 `switch_device()` + `get_available_devices()` |
| `server.py` | 新增 `POST /api/device/switch` + `GET /api/devices` |
| `index.html` | 设置页设备选择 UI + 状态栏联动 |
