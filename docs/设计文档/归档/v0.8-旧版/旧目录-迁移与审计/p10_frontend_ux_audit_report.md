# 桌伴 · Sidemate 前端 UX 审查报告

> 审查日期：2026-05-27 | 审查范围：`index.html` + `main.css` + 7个JS模块 (~3500行)  
> 审查维度：信息架构 / 布局响应式 / 视觉一致性 / 交互反馈 / 可用性无障碍 / 性能技术债务 / 内容文案

---

## 一、总览

桌伴是一个纯原生 HTML/JS 构建的本地 AI 助手，整体架构清晰、功能完整。但从 UX 角度看，存在**多套视觉系统并存、交互反馈缺位、无障碍性几乎空白、流式渲染性能瓶颈**等问题。以下按严重程度（🔴严重 → 🟡中等 → 🟢建议）列出 32 项具体问题。

---

## 二、信息架构 & 导航（3项）

### 🔴 1. 缺少首次使用引导（Onboarding）

**位置**: `index.html` 对话Tab 空状态  
**现状**: 对话Tab初始显示 `<div class="empty-state">开始对话吧</div>`，但没有任何操作指引。新用户不知道需要先去「设置」加载模型才能使用。

**影响**: 用户对着一个空白页面发呆，不知道下一步该做什么。

**建议**:
- 首次启动时（未加载模型 + 无历史对话）显示入门引导卡片：三步指引（加载模型 → 开始对话 → 探索其他功能）
- 空状态卡片包含直达「设置」的按钮，而非仅靠左上角的标签切换

---

### 🔴 2. Tab 功能发现性差 — 隐藏 vs 禁用（slow补充：这个不做！就是不安装不展示）

**位置**: `settings.js:669-729` `updateTabVisibility()`  
**现状**: 知识库/语音未安装时，对应的 Tab 按钮被 `display:none` 彻底隐藏。用户完全不知道这些功能存在。

**影响**: 功能可发现性为零。用户永远不会知道「这个应用还能做知识库问答和语音转写」。

**建议**:

- 改为显示Tab但标灰 + 禁用状态（`opacity: 0.4; cursor: not-allowed`），tooltip 显示「需安装扩展」
- 点击时弹出引导：提示前往「设置 → 扩展管理」安装
- 或在空状态区域展示功能预告卡片

---

### 🟡 3. 设置页信息过载，无分组折叠

**位置**: `index.html:405-587` 设置Tab  
**现状**: 系统状态、资源占用、模型管理、内存管理、扩展管理、Action管理、缓存管理、系统信息、版本信息——全部纵向堆在一个页面，滚动距离超过 1500px。

**建议**:
- 使用 Accordion/Collapse 组件按功能域分组（系统状态 / 模型与设备 / 扩展与插件 / 存储与缓存）
- 默认仅展开「系统状态」和「模型管理」，其余折叠
- 资源占用信息整合到 Header 区域（如系统托盘图标），减少设置页信息密度

---

## 三、布局 & 响应式（3项）

### 🔴 4. 移动端适配严重不足（slow补充，这个不做！只有桌面版本）

**位置**: `main.css` 全局布局  
**现状**: 唯一响应式断点是 `@media(max-width:600px)`，且仅覆盖 `.settings-grid` 一处。消息气泡 `max-width:90%` 在窄屏上过大；输入区域按钮过多导致换行；知识库左侧面板在窄屏上完全不可用。

**建议**:
- 增加 768px 断点（平板端），至少覆盖：
  - 消息气泡宽度收窄
  - 输入区按钮尺寸减小
  - 知识库面板改为底部抽屉/全屏覆盖
- 增加 1024px 断点，优化双栏布局

---

### 🟡 5. 知识库面板折叠状态体验不佳

**位置**: `qa.js:179-192`  `kbRefreshDocs()`  
**现状**: 首次打开知识库Tab且有文档时，300ms 后自动折叠左侧面板（slow确认保留此行为）。但折叠状态下仅显示 📂 + 数字计数，信息量几乎为零。

**影响**: 折叠后面板 36px 宽，用户看不到任何文档信息，只能凭记忆或点击展开。

**建议**:
- **保留**自动折叠逻辑（产品决策）
- 折叠状态优化：显示文档名称纵向滚动列表或缩略图标，而非仅数字
- 增加 `localStorage` 记忆上次展开/折叠状态，避免每次重新加载都回到折叠
- 折叠栏增加 tooltip 悬停预览

---

### 🟢 6. 全局 padding 不对称

**位置**: `main.css:81`  
**现状**: `#app{padding:6px 12px 5px}` — 上下 padding 不对称（6px vs 5px），且值过小导致内容紧贴窗口边缘。

**建议**: 统一为 `padding: 8px 12px`，或使用更大内边距提升呼吸感。

---

## 四、视觉设计 & 一致性（7项）

### 🔴 7. 按钮风格系统混乱 — 多套体系并存

**位置**: `main.css:224-261`  
**现状**: 项目中同时存在至少 5 套按钮样式系统：

| 体系 | 选择器 | 使用场景 |
|------|--------|---------|
| `.btn` + `.btn-primary` `.btn-danger` | `.btn` 系列 | 通用按钮 |
| `.panel button` + `.primary` `.secondary` `.danger` | `.panel button` | 纪要Tab |
| `.btn-send` `.btn-stop` `.btn-img` | 独立类名 | 对话输入区 |
| `.settings-btn` `.settings-btn-primary` | 设置特定 | 设置Tab |
| `.action-btn` `.action-btn.active` | Action特定 | ActionBar |

**影响**: 按钮圆角（3px/4px/6px/8px）、padding、颜色在不同Tab下表现不一致。用户需要适应多套视觉语言。

**建议**:
- 统一为单一按钮设计令牌系统：`btn` (基础) → `btn--primary` `btn--danger` `btn--ghost` `btn--small`
- 全局替换，保持 border-radius、padding、font-size 一致
- 删除旧的 `.panel button` 和 `.settings-btn` 映射

---

### 🔴 8. 深色/浅色模式主色调切换逻辑错误

**位置**: `main.css:3-49` (Light) vs `main.css:52-77` (Dark)  
**现状**: 
- Light 模式: `--accent-color: var(--primary-700)` = 深蓝 `#2d4a6f`
- Dark 模式: `--accent-color: var(--accent-600)` = 橙黄色 `#c9976c`

**这意味着：用户切换主题后，整个应用的视觉主色从蓝变橙。** 这是反直觉的——主题切换应该只改变明暗，而非改变品牌色。

**建议**: 深色模式保持相同的色相（蓝色系），仅调整亮度和饱和度：
```css
[data-theme="dark"] {
  --accent-color: #5b8cc9;  /* 蓝色系高亮，而非橙色 */
  --accent-hover: #7aa8dd;
}
```

---

### 🟡 9. 遮罩层设计不统一

**位置**: `index.html` 多处遮罩  
**现状**: 三个遮罩层存在显著风格差异：

| 遮罩 | 图标 | 背景 | 按钮风格 |
|------|------|------|---------|
| `chatModelOverlay` | 🔒 | `var(--overlay-bg)` | accent色填充按钮 |
| `kbModelOverlay` | 🔒 | `var(--overlay-bg)` | 文字链接（`<b>`） |
| `kbLockOverlay` | ⏳ | `var(--overlay-bg)` | 无操作按钮 |

**建议**: 统一为单一 `ModelLockOverlay` 组件，复用相同的样式和行为。

---

### 🟡 10. 滚动条未自定义，暗色模式下突兀

**位置**: 全局  
**现状**: 消息区、文档列表、历史记录等可滚动区域使用浏览器默认滚动条。在暗色模式下，白色/灰色原生滚动条出现在深色背景上，视觉割裂。

**建议**:
```css
/* 自定义滚动条 */
::-webkit-scrollbar { width: 6px; }
::-webkit-scrollbar-track { background: var(--bg-secondary); }
::-webkit-scrollbar-thumb { background: var(--border-color); border-radius: 3px; }
::-webkit-scrollbar-thumb:hover { background: var(--text-muted); }
```

---

### 🟡 11. 任务分类 Chip 暗色模式下颜色风格失控

**位置**: `main.css:142-151` (Light) vs `main.css:383-391` (Dark)  
**现状**: 暗色模式下的 chip 颜色（如 `#1e3a5f`、`#14532d`、`#451a03`）使用了 Tailwind 色板，与 Light 模式的浅色 chip 风格不统一。

**建议**: 暗色模式使用半透明背景 + 彩色文字，而非独立色板。

---

### 🟢 12. 代码块在 macOS/iOS 上使用 SF Mono，Windows 用户看到 Courier New（slow补充：要考虑离线使用情况，不能使用互联网资源）

**位置**: `main.css:168`  
**现状**: `font-family:'SF Mono',Monaco,monospace` 在 Windows 上退化为 Courier New（可读性差）。

**建议**: 因离线环境限制，只能使用系统自带等宽字体。Windows 兼容方案：
```css
font-family: 'Consolas', 'SF Mono', Monaco, 'Courier New', monospace;
```
`Consolas` 是 Windows 系统自带字体，可读性远优于 Courier New；macOS 退化为 SF Mono/Monaco。

---

### 🟢 13. 对话消息中思考过程详情样式过于朴素

**位置**: `main.css:179-181`  
**现状**: `<details>` 组件使用 `background:var(--bg-secondary); border-left:3px solid var(--border-color)`，与普通 markdown 内容区分度不够。思考过程是一个高级特性，应该有更好的视觉呈现。

**建议**: 思考过程使用独特的左侧色条（如紫色或渐变）+ 半透明背景 + 💭 图标前缀。

## 五、交互 & 反馈（7项）

### 🔴 14. 原生 alert()/confirm() 破坏体验

**位置**: 全局（`chat.js:107`, `qa.js:364`, `minutes.js:221`, `settings.js:402` 等多处）  
**现状**: 删除对话、删除文档、卸载模型等操作全部使用 `alert()` 和 `confirm()` 弹窗。这些弹窗:

- 阻塞主线程
- 无法自定义样式
- 在暗色模式下刺眼（白色弹窗）
- 无键盘快捷键支持

**建议**: 实现自定义 Modal 组件（类似 `transcriptModal` 但要轻量），支持:
- 非阻塞 UI
- 暗色模式适配
- Enter/Esc 键盘操作
- 危险操作的二次确认（如输入「删除」确认）

---

### 🔴 15. 流式渲染时强制拉到消息底部

**位置**: `chat.js:346-349` `appendStreamingMsg()`  
**现状**: 仅当 `distFromBottom < 80px` 时自动滚动到底部。但问题在于：
- 如果用户在阅读历史消息，新 token 到达时也会被强制拉到底部（因为滚动位置刚好 < 80px）
- 没有「用户已手动滚动离开」的状态追踪

**建议**: 
- 维护一个 `userScrolledUp` 标志位，当用户手动向上滚动时设为 true
- 仅当 `userScrolledUp === false` 时自动跟随滚动
- 当用户滚动回底部时自动恢复跟随

---

### 🟡 16. 缺少全局快捷键（slow补充：这个暂缓，先不做）

**位置**: 全局  
**现状**: 支持的快捷键仅有 `Enter` 发送（`chat.js:509`）。缺少：

| 快捷键 | 功能 |
|--------|------|
| `Ctrl+Enter` | 发送消息（备选） |
| `Shift+Enter` | 换行 |
| `Esc` | 关闭弹窗 / 停止生成 |
| `Ctrl+N` | 新建对话 |
| `Ctrl+K` | 聚焦输入框 |
| `Ctrl+/` | 显示快捷键帮助 |

**建议**: 实现 `KeyboardShortcuts` 模块，并在设置页/header 提供「快捷键」入口。

---

### 🟡 17. 消息发送后无视觉确认

**位置**: `chat.js:580-601` `sendMessage()`  
**现状**: 发送消息后输入框立即清空，消息出现在列表中。但没有任何过渡动画或确认反馈（发送按钮状态切换除外）。

**建议**: 消息气泡添加 `slideIn` 动画；发送按钮添加短暂的颜色闪烁或微动效。

---

### 🟡 18. Tab 切换无过渡动画

**位置**: `index.html:631-641` `switchTab()`  
**现状**: Tab 切换是即时替换 `display:none/active`，没有淡入淡出或滑动过渡。

**建议**: 添加 200ms 的 opacity 过渡，或使用 CSS `view-transition` API。

---

### 🟢 19. Toast 通知无法手动关闭、可能堆叠溢出

**位置**: `errors.js:65-92` `showToast()`  
**现状**: Toast 只有自动消失（默认4秒），没有关闭按钮。多个Toast垂直堆叠，在连续报错时可能溢出屏幕。

**建议**:
- 添加 ✕ 关闭按钮
- 限制最多同时显示 3 个 Toast
- 新Toast超出限制时移除最旧的

---

### 🟢 20. 模型加载进度指示与实际进度脱节

**位置**: `settings.js:780-820` `handleModelAction()`  
**现状**: 使用 SSE 加载进度条，但初始加载遮罩显示一个 8 秒的假进度条动画（`loadProgress` keyframe），然后才被真实的 SSE 进度覆盖。

**建议**: 移除预设动画，从一开始就显示「正在初始化...」+ indeterminate（不确定）进度条，直到 SSE 收到第一个 progress 事件。

## 六、可用性 & 无障碍（5项）

### 🔴 21. ARIA 无障碍标签几乎完全缺失（slow补充：这个不考虑）

**位置**: 全局  
**现状**: 

- 所有交互元素缺少 `aria-label`
- Tab 导航没有 `role="tablist"` / `role="tab"`
- 消息列表没有 `role="log"` / `aria-live`
- 动态内容更新没有 `aria-atomic` 通知
- 图标按钮（如 🗑、➕）没有文字替代

**影响**: 屏幕阅读器用户完全无法使用该应用。键盘导航用户无法在Tab之间切换。

**建议**: 系统性添加 ARIA 属性（按 WAI-ARIA 1.2 规范），至少覆盖：
```html
<div class="tabs-nav" role="tablist" aria-label="功能导航">
  <button role="tab" aria-selected="true" aria-controls="tab-chat">💬 对话</button>
</div>
<div id="messages" role="log" aria-live="polite" aria-label="对话消息"></div>
```

---

### 🟡 22. Focus 指示器不足

**位置**: `main.css` 全局  
**现状**: 仅 `textarea:focus` 和 `.btn:hover` 有视觉反馈。Tab 导航按钮、选择器、复选框等聚焦时无明显轮廓。

**建议**: 添加全局 `:focus-visible` 样式：
```css
:focus-visible {
  outline: 2px solid var(--accent-color);
  outline-offset: 2px;
}
```

---

### 🟡 23. 触控目标过小（移动端致命）（slow补充：这个不考虑，不涉及移动端）

**位置**: 多处（`main.css:110`, `main.css:169` 等）  
**现状**: 多处按钮 `padding:2px 6px`，实际可点击区域约 20x20px，远低于 WCAG 2.1 推荐的 44x44px 最小触控目标。

**建议**: 所有交互元素的触控区域至少 44x44px（或 24x24px for 紧凑UI）。小型按钮增大 padding 或添加伪元素扩大点击区域。

---

### 🟢 24. 颜色对比度未通过 WCAG AA 验证

**位置**: `main.css` 多处  
**现状**: 
- `--text-muted: #9ca3af` 在 `--bg-primary: #faf9f6` 上对比度约 2.7:1（AA要求 4.5:1）
- dark 模式 `--text-muted: #64748b` 在 `#0f172a` 上对比度约 3.9:1

**建议**: 使用 WCAG 对比度检查工具验证并调整：
- Light模式 `--text-muted` → `#6b7280` (对比度 4.6:1)
- Dark模式 `--text-muted` → `#94a3b8` (对比度 4.5:1)

---

### 🟢 25. 页面标题不随Tab切换变化

**位置**: `index.html:6`  
**现状**: `<title>桌伴 · Sidemate</title>` 始终不变，即使切换到不同Tab。

**建议**: `switchTab()` 中更新 `document.title`，如"对话 · 桌伴" / "文库 · 桌伴"，便于浏览器标签页区分。

## 七、性能 & 技术债务（3项）

### 🔴 26. renderMessages() 全量重绘 — 长对话性能灾难

**位置**: `chat.js:161-169` `renderMessages()`  
**现状**: 每次调用都用 `el.innerHTML = currentMessages.map(...).join('')` 重绘整个消息列表。在 100+ 条消息的对话中，这意味着每次新消息到达都要销毁并重建所有 DOM 节点。

**影响**: 
- 长对话时 UI 响应卡顿
- 丢失滚动位置、展开状态、选中状态
- 代码高亮（`applyCodeHighlight`）也需要重新应用

**建议**: 
- 实现增量渲染：新消息仅追加新 DOM 节点
- 引入虚拟列表（Virtual Scroll）或至少使用 `requestAnimationFrame` 批量更新
- 消息列表使用 key-based diff（简易版），只更新变化的消息

---

### 🟡 27. 多个轮询定时器同时运行

**位置**: 
- `chat.js:23-59` `startSessionPoll` — 每5秒
- `qa.js:311-316` `kbRefreshDocs` 轮询 — 每3秒
- `minutes.js:31-46` `_pollMinutesProgress` — 每2秒

**现状**: 最坏情况下，三个Tab切换后残留的定时器可能同时运行，每2秒发起 2 个请求，每5秒再发起 1 个。没有 Tab 失活时暂停轮询的机制。

**建议**:
- Tab 切换时清理非活跃 Tab 的定时器
- 使用 `visibilitychange` 事件（已部分实现）统一管理所有定时器
- 考虑用 WebSocket 替代轮询（如果后端支持）

---

### 🟡 28. md() 函数在流式渲染中重复解析全文本

**位置**: `utils.js:131-188` `md()` + `chat.js:309-349` `appendStreamingMsg()`  
**现状**: 每收到一个 SSE token（约 80ms 间隔），`appendStreamingMsg()` 把完整的 `fullText` 传入 `md()` 重新解析。这意味着每次都要重新运行整个 Markdown 解析管道（代码块、LaTeX、列表等）。

**建议**:
- 缓存上一次解析结果，仅处理新增部分
- 或使用 `requestAnimationFrame` 合并 16ms 内的多次更新
- 考虑使用 Web Worker 卸载 Markdown 解析

---

## 八、内容 & 文案（4项）

### 🟡 29. 术语不一致（slow补充：以Tab名为主！文库、纪要！）

**位置**: 全局  
**现状**: 同一概念在不同位置使用不同称谓：

| 概念 | Tab名（官方名称） | 代码/文案中混用 |
|------|-------------------|----------------|
| 文库 | 「📚 文库」 | 内部代码称「知识库」「KB」「qa」|
| 纪要 | 「📝 纪要」 | 安装页称「语音转写模块」|
| 深色模式 | 「深色模式」 | 变量名 `dark` |
| 模型 | — | 「AI模型」「主模型」「LLM」混用 |

**建议**: **以Tab名为唯一权威术语**，反向统一：
- 所有面向用户的文案中「知识库」→「文库」（代码内部变量名 `kb` 可保留）
- 所有面向用户的文案中「语音转写」→「纪要」
- AI模型 → 统一为「AI模型」
- 制定术语表写入 `README.md` 供团队参考

---

### 🟡 30. 空状态引导文案不足

**位置**: 多处空状态  
**现状**: 

| 空状态 | 当前文案 | 问题 |
|--------|---------|------|
| 对话Tab | "开始对话吧" | 无操作引导 |
| 知识库问答 | "先从左侧上传文档..." | 但用户可能不知道左侧是什么 |
| 纪要历史 | "暂无录音记录" | 无操作引导 |

**建议**: 空状态应包含：
1. 当前状态说明（发生了什么）
2. 下一步操作（该做什么）
3. 行动按钮（一键直达）

### 🟢 31. 导出功能命名混淆

**位置**: `minutes.js:782-851`  
**现状**: `saveMinutesAs('docx')` 实际输出的是 `.doc` 格式（`application/msword` MIME），不是 `.docx`。

**建议**: 修正 MIME 类型为真正的 `.docx` 格式，或将按钮文案改为「存为 DOC」。

### 🟢 32. 错误信息对终端用户不友好

**位置**: 各处 `catch` 块  
**现状**: 技术性错误信息被直接展示给用户，如「服务器错误 (500)」「请求超时 (10s)」「Cannot read properties of undefined」。

**建议**: 建立错误信息映射表，将技术错误转换为用户友好的中文提示：
- `500` → "服务处理出错，请稍后重试"
- 超时 → "服务响应较慢，请确认后台正在运行"
- 网络错误 → "无法连接服务，请检查是否已启动"
