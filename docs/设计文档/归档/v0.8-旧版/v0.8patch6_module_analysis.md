## 一、知识库模块 (knowledge_base.py)

### 1.1 现状总览

| 维度 | 现状 | 评价 |
|------|------|------|
| 嵌入引擎 | bge-base-zh-v1.5 (768维) 优先，TF-IDF (char_wb, 512维) 降级 | 双模式设计合理，但bge依赖sentence-transformers+torch，离线兼容性有风险 |
| 检索 pipeline | Hybrid Search (向量+BM25) → RRF融合 → Reranker精排 → 自适应融合 → MMR多样性 | 多层pipeline保障精度，Reranker+MMR在办公文档场景下有效抑制幻觉 |
| 精排引擎 | bge-reranker-base CrossEncoder，CPU运行 | ~400MB内存占用可接受，专用模型精度优于8B通用模型重排，保留 |
| 向量存储 | numpy矩阵 (N, dim)，npz压缩存储 | 1000 chunk × 768维 ≈ 3MB，当前规模够用，但无索引加速 |
| 文档处理 | 分块→嵌入→摘要，串行化摘要锁 | 多文档导入时摘要排队，体验不佳 |
| 前端状态机 | 三级：未安装→已安装未激活→已激活 | 设计清晰，但State 1/2之间切换偏重型 |
| 问答模式 | 独立Tab，流式SSE输出，引据式prompt | 与对话Tab割裂，办公场景中切换成本高 |

### 1.2 改进空间详细分析

#### 【P0】嵌入模型技术栈统一（架构）

**问题**：
- bge模型通过 `sentence_transformers.SentenceTransformer` 加载，底层依赖 PyTorch
- 主模型(Qwen3-8B)已用 OpenVINO GenAI 运行时，技术栈不统一
- 离线环境下 PyTorch + OpenVINO 双运行时并存，增大打包体积、增加兼容性风险
- sentence-transformers 版本与 PyTorch 版本耦合，升级时容易踩坑

**影响**：
- 知识库模块安装包需要包含 torch+sentence-transformers，体积从~300MB膨胀到~1.5GB
- 某些Windows环境 PyTorch CPU wheel 安装失败会导致整个知识库不可用
- 与项目"轻量本地部署"目标冲突

**建议方案**（按优先级排序）：

| 方案 | 工作量 | 效果 | 推荐度 |
|------|--------|------|--------|
| A. bge转ONNX，OpenVINO推理 | 2-3天 | 统一技术栈，~90MB模型，OpenVINO CPU推理速度优于PyTorch | ★★★★★ |
| B. 提供纯numpy轻量替代 | 1-2天 | 预计算词向量表(Top 5万中文词)，无torch依赖，精度略降但可用 | ★★★★☆ |
| C. 维持现状，但优化打包 | 半天 | 将torch设为optional依赖，TF-IDF作为默认，bge为增强选项 | ★★★☆☆ |

> 推荐走 **方案A**：bge-small-zh-v1.5 已有社区ONNX版本，转换脚本成熟。OpenVINO对ONNX Embedding模型的推理优化很好，且与主模型统一运行时。

#### 【P1】检索Pipeline参数调优（架构）

**现状**：
当前检索链路：
```
Query → 向量检索(top_k×2) + BM25检索(top_k×2) → RRF融合 → Reranker打分 → 自适应NDCG融合 → MMR多样性 → 取top_k
```
共5层，Reranker和MMR对精度保障有明确价值，**保留不动**。

**8B模型 vs 专用Reranker**：
- 8B通用模型做重排：任务边界模糊，易将训练偏见带入排序；对长文档片段的细粒度相关性判断不稳定
- bge-reranker-base CrossEncoder：专为相关性排序训练，输入`[问题, 片段]`输出单一分数，任务单一、输出稳定
- **结论**：在8B模型幻觉风险较高的场景下，专用Reranker是精度护城河，不能省

**优化空间**（不调架构，只调参数）：

1. **向量阈值偏低**：代码中 `VECTOR_SCORE_THRESHOLD = 0.25`，bge-base-zh在中文语义匹配中0.25偏低，部分噪声片段会进入后续环节。建议根据实测调整为 **0.28-0.30**，在召回率和精确率之间取平衡。

2. **top_k 倍数偏大**：当前向量+BM25各取 `top_k×2`（即若最终要5篇，各取10篇），Reranker要处理20篇。可优化为 `top_k×1.5`（各取8篇），Reranker处理16篇，减少无谓计算而不影响精度。

3. **BM25依赖jieba+rank_bm25**：jieba分词对英文/数字混合文本效果一般，但办公文档以中文为主，当前够用。若后续中英混杂文档增多，再评估替换为 `scikit-learn` 的 `TfidfVectorizer`（已依赖，无需新增包）。

**建议**：
- **Reranker保留**，MMR保留，不做减法
- 调参：`VECTOR_SCORE_THRESHOLD` 从 0.25 → 0.28（实测验证）
- 调参：粗筛 `top_k` 倍数从 ×2 → ×1.5
- 目标：在**不降低精度**的前提下减少 10-15% 的无效计算

#### 【P1】对话Tab与知识库打通（产品）

**问题**：
- 知识库问答在独立的"问答Tab"，对话在"对话Tab"
- 办公场景中，用户不会严格区分"查资料"和"聊天"，而是自然地混合进行
- 例如："根据上周的会议纪要，帮我写个邮件通知大家"——这需要同时使用知识库(会议纪要)和对话(邮件撰写)

**现状交互成本**：
1. 切到问答Tab → 搜索/提问 → 复制答案
2. 切回对话Tab → 粘贴答案 → 继续提问
3. 如果答案不够用，再切回问答Tab...

**设计原则**：
- **保留现有问答Tab**：降低老年用户/新用户学习成本，独立Tab界面直观，不用记指令
- **对话Tab增加 `/kb` 指令作为补充**：为熟练用户提供快捷路径，不打断对话流

**建议方案（Patch 6）**：

**① 保留问答Tab，不做精简**
- 问答Tab继续承担"文档管理 + 知识库检索问答"核心功能
- 独立Tab降低认知负担，用户不需要学习任何指令

**② 对话Tab新增 `/kb` 快捷指令**
```
用户输入："/kb 上周会议纪要中关于预算的讨论"
→ 后台自动检索知识库 → 将Top3片段作为上下文注入对话
→ 8B模型基于片段生成回答
→ 用户无需切Tab，对话流不中断
```
- 仅当用户主动输入 `/kb` 前缀时触发，不自动干预普通对话
- 8B模型任务明确（"基于以下片段回答问题"），幻觉可控

**③ 追问能力（见下方P2）**
- `/kb` 查询后，用户可继续追问"那试用期呢？"
- 通过轻量级多轮状态跟踪，将追问展开为完整检索query

#### 【P2】文档摘要生成阻塞可用性（体验）

**问题**：
```python
# process_document() 中
with self._summary_lock:  # 串行锁！
    doc.status = "summarizing"
    summary = self._generate_doc_summary(doc_id, new_chunks)
    doc.status = "ready"
```

- 文档分块+嵌入完成后，必须等摘要生成才能变为"ready"
- 摘要生成调用8B模型，每篇文档10-30秒
- 如果用户一次导入5个文档，最后一个文档要等前面4个摘要都完成才能用
- 但摘要只是"锦上添花"的功能，不影响检索和问答

**建议**：
- **异步化摘要**：分块+嵌入完成后立即标记为"ready"，摘要放到后台队列慢慢生成
- **摘要状态独立**：增加 `summary_status` 字段（pending/generating/done/failed），与 `doc_status` 解耦
- **无摘要也可检索**：摘要虚拟chunk（index=-1）不阻塞主流程

#### 【P2】缺乏文档增量更新（功能）

**问题**：
- 文档导入后只能删除重新导入
- 办公场景中文档经常更新（如"项目周报_第3周.md"→"项目周报_第4周.md"）
- 用户被迫保留旧版本+导入新版本，占用双份额度

**建议**：
- 增加 `/api/kb/documents/{doc_id}/update` 接口
- 实现增量分块：对比新旧文本，只更新变化的chunk，保留不变的chunk向量
- 或者至少提供"替换导入"：删除旧版+导入新版作为一个原子操作，不占用双份额度

#### 【P2】PDF扫描件不支持（功能）

**问题**：
- 当前PDF解析用 pdfplumber / pypdf，仅提取文本层
- 办公场景中大量PDF是扫描件（图片PDF），无文本层
- 扫描件PDF导入后内容为空，用户困惑

**建议**：
- 导入PDF时检测是否为扫描件（尝试提取文本，如果字数<100则判定为扫描件）
- 扫描件自动调用已有OCR能力（RapidOCR）提取文字
- 在文档列表中标注"已OCR"状态

#### 【P2】知识库问答无追问能力（功能）

**问题**：
- KB问答保留最近4轮历史，但只是简单拼接
- 不支持真正的多轮上下文理解：
  - 用户："公司年假政策是什么？"
  - AI："根据员工手册，年假为5-15天..."
  - 用户："那试用期有吗？" ← 指代"年假"，但当前实现无法关联
- `kb_prompt` 中没有注入前一轮的问答内容作为上下文

**方案设计（适配8B模型，轻量级）**：

**① 追问识别（8B模型做结构化判断）**

不是让8B自由生成，而是做**填空式判断**——任务单一，8B胜任：

```text
判断用户输入是否是"追问"（依赖上文才能理解）。

上文问题：{last_query}
上文回答摘要：{last_answer[:200]}
用户输入：{current_input}

请输出JSON：
{
  "is_followup": true/false,
  "resolved_query": "如果is_followup=true，输出展开后的完整问题；否则输出原input",
  "reason": "判断理由（50字内）"
}

规则：
- 包含指代词（那/这个/它/他/上述/前面说的）→ is_followup=true
- 省略主语但依赖上文主题 → is_followup=true
- 完全独立的新问题 → is_followup=false
```

8B模型对这种结构化判断准确率 > 90%，且输出JSON格式稳定。

**② 追问状态存储（前端维护，无后端负担）**

```javascript
// 前端对话session中维护
_kbContext = {
  lastQuery: "年假有多少天",
  lastAnswer: "根据员工手册，年假为5-15天...",
  lastResults: [chunk1, chunk2, chunk3],  // 上轮检索的Top3片段
  isActive: true  // 最近一轮是/kb查询，处于可追问状态
};
```

- 普通对话（非 `/kb`）后 `_kbContext.isActive = false`
- `/kb` 查询后 `_kbContext.isActive = true`
- 用户输入不含 `/kb` 前缀但 `_kbContext.isActive === true` 时 → 走追问流程

**③ 追问处理流程**

```
用户输入："那试用期呢？"（无 /kb 前缀，但 _kbContext.isActive=true）

Step 1: 前端发送 /api/chat/stream，附加字段：
  { message: "那试用期呢？", kb_context: _kbContext }

Step 2: 服务端调用8B模型做追问识别（Prompt见①）
  → 输出：{"is_followup": true, "resolved_query": "试用期有年假吗？"}

Step 3: 用 resolved_query 独立检索知识库（不依赖历史检索结果）
  → 新 Top3 片段

Step 4: 构造 Prompt：
  "用户之前问：{last_query}\n"
  "AI回答：{last_answer[:100]}...\n"
  "用户追问：{resolved_query}\n\n"
  "参考资料：\n{新Top3片段}\n\n"
  "请基于参考资料回答追问。"

Step 5: 流式生成回答，前端更新 _kbContext
```

**④ 关键设计决策**

| 决策 | 选择 | 理由 |
|------|------|------|
| 追问识别放在服务端还是前端？ | **服务端（8B模型）** | 前端判断不准，8B理解上下文能力强 |
| 追问时检索用原query还是展开query？ | **展开query独立检索** | 避免历史检索结果的偏见，每次追问都是独立检索 |
| 追问状态保存多久？ | **直到用户发起非/kb的普通对话** | 简单清晰，不引入session超时复杂度 |
| 8B模型负担？ | **极低** | 追问识别是结构化填空，不是开放生成，耗时 < 500ms |

**⑤ 与 `/kb` 指令的关系**

- `/kb 年假政策` → 显式触发，独立检索，回答后进入"可追问"状态
- `那试用期呢？` → 隐式追问，前端检测到可追问状态 → 走追问流程
- `帮我写个邮件` → 普通对话，前端将 _kbContext.isActive 置 false，不再误判为追问

#### 【P3】向量检索无索引加速（性能）

**问题**：
- 当前向量检索是O(N)的全量点积： `np.dot(self.vectors, query_vec.T)`
- 1000个chunk时完全没问题，但如果有5000+ chunk呢？
- 按设计上限 `max_total_chunks=1000`，当前不紧急

**建议**：
- 预留 `faiss-cpu` 集成接口（可选依赖）
- 当chunk数>2000时自动启用faiss IVF索引
- 保持numpy作为fallback

### 2.2 改进空间详细分析

#### 【P0】8B纠错批次上下文断裂（正确性）

**问题**：
```python
# _refine_with_llm() 中
batch_chars = 800  # 每批800字
chunks = [rough_draft[i:i+batch_chars] for i in range(0, len(rough_draft), batch_chars)]
for idx, chunk in enumerate(chunks):
    prompt = "修正这段文本的错别字..."  # 每批独立prompt！
    result = model.chat_stream(messages=[{"role":"user","content":prompt}])
```

- 每批800字独立调用LLM，批与批之间**零上下文共享**
- 会议中常见的指代表达会断裂：
  - Batch 1: "这个方案我已经和张总讨论过了"
  - Batch 2: "他认为预算方面需要再压缩" ← "他"指谁？模型不知道
  - Batch 3: "那我们下周再碰一次" ← "那"指什么？模型不知道
- 专有名词一致性也无法保证：Batch 1把"Kubernetes"错成"库伯内特"，Batch 2可能"修正"成另一个版本

**影响**：
- 纠错后的文本虽然单看每批都没问题，但整篇连贯性下降
- 会议纪要生成基于纠错稿，断裂会传导到纪要质量

**建议方案**：

| 方案 | 描述 | 工作量 | 推荐度 |
|------|------|--------|--------|
| A. 滑动窗口重叠纠错 | 每批1000字，重叠200字（前批尾→下批头），让模型看到上下文 | 半天 | ★★★★★ |
| B. 全文一次性纠错 | 如果转写稿<4000字，直接一次性纠错；只有超长才分批次 | 半天 | ★★★★☆ |
| C. 术语一致性后处理 | 纠错后增加一轮"术语统一"：提取全文专有名词→统一写法 | 1天 | ★★★☆☆ |

> 推荐 **方案A+B结合**：短文稿(<4000字)一次性纠错；长文稿用滑动窗口重叠纠错。

#### 【P1】会议纪要模板单一（功能）

**问题**：
```python
prompt = (
    "将以下会议/谈话转写稿整理为结构化会议纪要。\n\n"
    "要求：\n"
    "1. 一句话总结会议主题\n"
    "2. 列出3-5个关键要点\n"
    "3. 列出待办事项（如有）\n"
    "4. 列出决策结论（如有）\n"
)
```

- 所有会议用同一模板，无论周会/评审会/1on1/头脑风暴
- 没有说话人分离（speaker diarization）
- 没有时间戳标记（无法"点击文本跳转到录音位置"）
- 没有会议类型自动识别

**办公场景需求**：

| 会议类型 | 纪要重点 | 当前支持 |
|----------|----------|----------|
| 项目周会 | 进度更新、 blocker、下周计划 | 基本可用 |
| 需求评审 | 评审结论、待修改点、责任人 | 无结构化 |

**建议**：
1. **多种纪要模板**：用户在生成纪要前选择模板类型（或AI自动识别）

3. **时间戳标记**：转写文本保留segment开始/结束时间，纪要中关键句可点击跳转录音
4. **纪要导出**：支持导出为markdown/docx，方便邮件发送或存档

#### 【P1】转写稿与录音零联动（体验）

**问题**：
- 查看转写稿时只能看到纯文本
- 无法"点击某句话 → 播放对应录音段落"
- 办公场景中经常需要"听原声确认"
- `segments_iter` 返回的数据中包含时间戳，但后端没有保存到session

**现状数据流**：
```
Whisper segments → 只提取text → 拼接成rough_draft → 丢弃时间戳
```

**建议**：
- 在 `RecordingSession` 中增加 `segments` 字段：`[{start, end, text, speaker?}]`
- 前端展示转写稿时，每句话带时间戳标记
- 点击时间戳调用 `<audio>` 播放对应片段（使用 `audio.currentTime` 跳转）
- 会议纪要生成时保留关键决策的时间戳引用

#### 【P1】实时转写体验不足（体验）

**问题**：

#### 【P2】Whisper扩展包依赖风险（架构）

**问题**：
- faster-whisper依赖CTranslate2，CTranslate2需要编译好的wheel
- Windows上CPU版wheel体积大，某些Python版本可能无预编译包
- 扩展包安装流程中 `install.py` 需要本地编译，出错率高

**替代方案对比**：

| 方案 | 体积 | 速度 | 准确率 | 离线兼容性 | 推荐度 |
|------|------|------|--------|------------|--------|
| faster-whisper (当前) | ~500MB | 快 | 85% | 依赖CTranslate2 wheel | ★★★☆☆ |
| whisper.cpp (ggml) | ~150MB | 中等 | 82% | 纯C++，ctypes加载，零Python依赖 | ★★★★★ |
| OpenVINO Whisper | ~500MB | 快(CPU) | 85% | 统一OpenVINO运行时 | ★★★★☆ |
| 本地小模型(自己训) | ~100MB | 快 | 70% | 完全可控 | ★★☆☆☆ |

> **推荐评估 whisper.cpp**：Intel有openvino-whisper项目，可以用OpenVINO runtime跑Whisper。如果能统一到OpenVINO运行时，整个项目就只剩一个推理框架。

### 3.1 知识库 × 录音纪要

**未打通点**：

| 场景 | 现状 | 改进 |
|------|------|------|
| 会议中提到的决策直接加入知识库 | 需手动入库→手动提问 | 会议纪要生成时自动提取"决策结论"→写入记忆/知识库 |
| 会议纪要中的待办自动创建提醒 | 无 | 纪要中"待办事项"→转换为待办列表（个性Tab中展示） |
| 录音中提到的人名自动更新用户画像 | 无 | 转写稿中提取"提到的人/组织/项目"→建议用户确认后写入记忆 |

### 3.2 知识库 × 对话Tab

**Patch 6 方案**：显式 `/kb` 指令（保留问答Tab）
```
用户主动输入 "/kb 上周会议纪要中关于预算的讨论"
→ 前端识别 /kb 前缀 → 提取 query → 调用 /api/chat/stream（带 kb_query 字段）
→ 服务端检索知识库 Top3 → 注入上下文 → 8B模型基于片段回答
```

**为什么不自动RAG？**
- 8B模型对"是否需要查资料"的判断不稳定，容易误触发或漏触发
- 自动检索会增加对话延迟（每次对话都要判断是否检索）
- 显式 `/kb` 让用户有掌控感，8B任务边界清晰，幻觉可控

**实现关键点**：
- 前端：输入框检测 `/kb ` 前缀 → 截断提取 query → 请求体增加 `kb_query` 字段
- 服务端：`api_chat_stream()` 中若 `kb_query` 非空 → 调用 `kb.search()` → 片段拼入 system prompt
- 追问：前端维护 `_kbContext` 状态 → 无 `/kb` 前缀但处于追问状态 → 服务端 8B 判断 `is_followup` → 展开 query → 独立检索

### 3.3 录音纪要 × 对话Tab

**改进方向**：语音输入
```
对话Tab增加🎙️按钮 → 按住说话 → 实时转写 → 文本填入输入框 → 自动发送
```

这比D28的"实时语音对话"更轻量，不需要全双工交互，只是替代键盘输入。
