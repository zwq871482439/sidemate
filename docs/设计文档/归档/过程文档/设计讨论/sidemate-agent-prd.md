> 作者：许清楚（Xu） | 版本：1.0 | 日期：2026-06-07

---

## 一、产品目标

### 1.1 一句话目标

将 Sidemate 在线模式从"固定 Pipeline 的文本生成器"升级为"自主决策的 Agent"，让云端大模型真正发挥推理和工具调用能力。

### 1.2 核心问题

当前在线模式（cloud）将 GLM-5.1、DeepSeek 等大模型当"最后一段文本生成器"使用——模型只负责在固定 Pipeline 末端生成文字，没有自主决策权，无法主动调用工具、无法规划任务、无法多步推理。

### 1.3 成功指标

| 指标 | 目标 |
|------|------|
| 在线模式能自主完成多步任务（搜索→分析→写作） | 是 |
| 文档生成由 Agent 自主规划工具调用，而非固定工具链 | 是 |
| 用户可实时看到 Agent 正在做什么（状态指示器） | 是 |
| 本地模式功能完全不受影响 | 是 |
| FC 兼容性故障能 graceful fallback | 是 |

## 二、目标用户

Sidemate 的核心用户是**本地办公场景的个人用户**，他们：
- 需要一个能离线运行的 AI 助手（隐私、断网可用）
- 同时也希望在联网时获得更强的大模型能力
- 不是技术专家，不想手动配置工具和 Prompt

---

## 三、用户故事

### US-1: 智能对话

> 作为用户，当我选择"智能对话"时，Agent 能自主决定是否需要搜索、查知识库、分析文件，而不是只能聊天。

**场景**：用户问"最近有什么关于 Rust 1.85 的新特性？"，Agent 自主决定调用搜索引擎查找，综合结果回答。

### US-2: 文档生成

> 作为用户，当我选择"文档生成"时，Agent 拿着全套工具自主写作——搜索资料、分析内容、组织结构、生成文档——而不是走固定的 Outline→Draft→Refine 三步。

**场景**：用户说"帮我写一份 Rust 异步编程技术调研报告"，Agent 自主决定先搜索 Rust 异步生态，再整理要点，最后输出文档。

### US-3: 实时状态反馈

> 作为用户，当 Agent 在思考和调用工具时，我能实时看到它在做什么——"正在搜索…"、"正在分析网页…"——而不是对着空白屏幕干等。

### US-4: 任务完成摘要

> 作为 Agent 完成任务后，我希望能看到本次任务的统计摘要——调用了几次搜索、读了几个网页、花了多长时间——帮助我理解 Agent 的工作过程。

### US-5: 本地模式不受影响

> 作为用户，当我切换回本地模式时，一切照旧。我的 3 个按钮（智能对话 / 知识库问答 / 文档生成）还在，小模型的防护栏（漂移检测、语义截断、自动续写）还在。

### US-6: 会话数据不丢失

> 作为用户，升级后我的历史会话数据能自动迁移到新格式，不需要手动操作。

| P0-5 | **前端状态指示器**：agent_status SSE 事件 + 旋转动画 | US-3 | Agent 调用工具时前端显示"正在搜索…"等状态 |

| P0-8 | **文档生成 Agent 化**：Agent 拿着全部工具自主写作，不复用本地模式流程 | US-2 | 文档生成完全由 Agent 自主规划，仅复用 python-docx 输出层 |

## 五、功能规格

### 5.1 Agent Loop 行为

```
用户消息
  │
  ▼
AgentLoop
  ├─ 1. 组装 System Prompt（动态工具注册）
  ├─ 2. 调用 CloudEngine（带 tools 参数）
  │     ├─ 模型返回 FC 调用 → 执行工具 → 将结果加入 messages → 回到 2
  │     └─ 模型返回正文 → 结束循环
  ├─ 3. 最大循环次数：15 轮（防止无限循环）
  └─ 4. 输出 SSE 事件流
```

### 5.2 在线模式 UI

**当前**：3 个按钮（智能对话 / 知识库问答 / 文档生成）

**改为**：2 个按钮
- **智能对话**：Agent 模式，自动决定是否搜索/查知识库
- **文档生成**：Agent 模式，自主规划文档写作流程

知识库问答不再作为独立入口，而是由 Agent 在智能对话中自主决定是否查知识库。

### 5.3 SSE 事件协议

| 事件 | 触发时机 | 数据格式 |
|------|---------|---------|
| `agent_think` | Agent 推理过程（模型 reasoning_content） | `{"content": "..."}` |
| `agent_status` | Agent 调用工具/状态变化 | `{"status": "searching", "detail": "搜索 Rust 异步..."}` |
| `agent_summary` | 任务完成后 | `{"tool_calls": 3, "searches": 2, "pages_read": 1, "time": 12.5}` |

### 5.4 工具清单（Agent 可用）

**智能对话模式**：
- `web_search(query)` — 网页搜索
- `web_fetch(url)` — 抓取网页内容
- `kb_search(query)` — 知识库检索

**文档生成模式**：
- 以上全部 +
- `write_section(title, content)` — 写入文档章节
- `search_and_summarize(query)` — 搜索并总结

### 5.5 会话存储新格式

```
data/chats/
  my-chat/
    meta.json          # 会话元信息（创建时间、模型、模式）
    messages.json      # 消息历史（含 agent 工具调用记录）
    assets/            # 附件（生成的文档、图片等）
```

迁移策略：启动时扫描旧格式 `.json` 文件，自动转为文件夹格式。

## 六、非功能需求

| 维度 | 要求 |
|------|------|
| 兼容性 | 不破坏任何本地模式功能 |
| 性能 | Agent Loop 每轮工具调用 < 30s 超时 |
| 可靠性 | FC 错误自动 fallback，不暴露错误给用户 |
| 数据安全 | 会话迁移原子操作，失败时保留原文件 |
| 可维护性 | 在线/离线代码路径完全隔离 |

## 七、已确认的架构决策（不需要讨论）

1. 在线模式 Pipeline → ReAct Agent Loop
2. 工具调用协议：OpenAI Function Calling JSON
3. System Prompt 动态组装
4. 三层架构：CloudPipeline → AgentLoop → CloudEngine
5. SearchEngine 升级：httpx → curl_cffi（最后做，有 fallback）
6. 前端实时状态指示器（agent_status + 旋转动画）
7. 前端最终统计摘要（agent_summary）
8. 文档生成：Agent 自主写作，仅复用 python-docx 输出层
9. 会话存储：JSON 文件 → 文件夹，启动自动迁移
10. 在线模式 2 按钮 / 本地模式 3 按钮
11. SSE 事件：agent_think / agent_status / agent_summary
12. 不做用户可配置工具系统
13. 在线/离线模式完全独立
14. FC 兼容性：运行时错误捕获 fallback
15. Phase 1-5 一次性全部实施，最后统一回归测试
16. curl_cffi 最后做

## 九、待确认问题

| # | 问题 | 背景 | 建议 |
|---|------|------|------|
| Q1 | Agent Loop 最大轮次设为多少？ | 防止无限循环和 token 消耗 | 建议 15 轮，可配置 |
| Q2 | 文档生成的输出格式是否仍然仅支持 .docx？ | 当前仅 python-docx | Phase 1 保持 .docx，后续可扩展 |
| Q3 | 知识库工具在无 KB 文档时是否注册？ | Agent 可能尝试调用但无数据 | 建议有文档时才注册 kb_search |
| Q4 | Agent 工具调用的超时策略？ | 网页抓取可能很慢 | 建议搜索 15s、抓取 20s、总任务 5min |
| Q5 | agent_summary 事件是否需要持久化到会话历史？ | 便于回看任务统计 | 建议存入 meta.json |
| Q6 | 会话迁移失败时是否提示用户？ | 自动迁移可能因权限等原因失败 | 建议静默失败，保留原文件，记日志 |

## 十、风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 模型 FC 能力参差不齐 | 部分 API 提供商的 FC 实现有 bug | 运行时错误捕获 + fallback 到普通对话 |
| Agent Loop token 消耗大 | 用户 API 费用增加 | 设最大轮次，agent_summary 显示消耗 |
| SSE 事件格式变化导致前端异常 | 前端崩溃 | 精简到 3 个核心事件，前后端同步测试 |
| 会话迁移数据丢失 | 用户历史对话丢失 | 原子迁移，失败保留原文件 |
