### 2.2 list_kb_docs 工具

**脱敏设计**：不暴露文件名，只返回结构化概览。

```json
// 工具定义
{
  "name": "list_kb_docs",
  "description": "查看本地知识库中的文档概览（主题摘要、章节结构），用于判断是否需要检索知识库以及生成精准的搜索关键词",
  "parameters": { "type": "object", "properties": {}, "required": [] }
}

// 返回格式
{
  "documents": [
    {
      "doc_id": "d4f3a1",
      "summary": "涵盖中医经络理论、刮痧/拔罐/艾灸等疗法操作指南",
      "headings": ["经络基础", "刮痧手法", "穴位速查"],
      "snippets": ["中医经络理论是...", "刮痧的基本手法..."],
      "chunks": 42,
      "chars": 18000,
      "status": "ready"
    }
  ],
  "total_docs": 1,
  "total_chunks": 42
}
```

**status 三值**：

| status | 含义 | list_kb_docs 返回 |
|--------|------|------------------|
| `searchable` | 可检索，无摘要 | headings + snippets（方案 γ 兜底） |
| `summarizing` | 摘要进行中 | headings + snippets + partial summary + 进度% |
| `ready` | 全功能 | headings + full summary |

### 2.3 文档摘要方案（方案 δ — 批量采样摘要）

#### 核心原则

**摘要永远走本地 LLM**，不上传到云端。原因：
- KB 的核心理念是数据不出本机
- 上传文档到 KB 就是为了隐私，摘要再发云端就矛盾了

#### 粒度：批量采样

```
文档 12 个 chunk → 合并为 ~6 个 batch（每个 batch ~1500-2500 字）
                → 每个 batch 一次 LLM 调用（~150 字摘要）
                → 所有 batch 摘要合并为文档级 summary

batch 合并策略：
  - 相邻 chunk 合并，直到达到 ~2000 字
  - 所有 chunk 必须被覆盖（不跳过任何一个）
  - 长文档可能产生很多 batch，全部覆盖
```

#### 入库流程（改动后）

```
上传文档 → 提取文本 → 分段 → 嵌入向量化 → 可搜索 ✅
                     ↓
              立即执行（零 LLM 成本）：
              → 提取标题层级（docx H1/H2/H3、PDF 书签、md #）
              → 提取每个 chunk 前 50 字作为 snippet
              → 存入 metadata.headings + metadata.snippets
              → status = "searchable"（立即可检索+可见）
                     ↓
              异步摘要流程（需要本地 LLM）：
              → batch 划分：相邻 chunk 合并到 ~2000 字
              → 逐 batch 调用本地 LLM 生成摘要
              → 每完成一个 batch → 保存断点 → 更新进度%
              → 全部完成 → 合并为文档 summary
              → status = "ready"
```

#### S3 隐身文档问题的解决

**问题**：在线模式 + LLM 未预热时，文档可检索但无摘要，云端大模型看不到文档存在。

**解决**：方案 γ（标题提取）兜底 — 上传时立即提取 headings + snippets，零 LLM 成本：

```
即使没有摘要，list_kb_docs 也会返回：
  headings: ["经络基础", "刮痧手法", "穴位速查"]
  snippets: ["中医经络理论是...", "刮痧的基本手法..."]
  summary: null（待生成）
  status: "searchable"
```

云端大模型看到 headings + snippets 就能判断文档主题，不需要等摘要。

#### 断点续传设计

```json
// 文档元数据存储（per doc）
{
  "doc_id": "d4f3a1",
  "summary": null,
  "summary_status": "pending",        // pending | in_progress | done | failed
  "summary_progress": {
    "total_batches": 6,
    "completed_batches": 3,
    "batch_summaries": [
      "涵盖中医经络理论基础...",
      "详细介绍十二正经走向...",
      "刮痧疗法的操作手法..."
    ]
  }
}
```

**断点续传流程**：

```
第一次运行：
  batch 1 → 完成 → 存 batch_summaries[0]
  batch 2 → 完成 → 存 batch_summaries[1]
  batch 3 → 完成 → 存 batch_summaries[2]
  → 用户退出程序

第二次启动：
  读 summary_progress → completed_batches=3
  → 从 batch 4 继续
  batch 4-6 完成 → 调合并 LLM → summary = "涵盖..."
  → summary_status = "done"
```

**失败处理**：
- 单个 batch LLM 调用失败 → 不存，下次重试同一 batch
- 合并步骤失败 → batch_summaries 保留，下次重试合并
- 前端提供"重新生成摘要"按钮 → 清空 summary + progress，从头开始

#### 前端 UI

```
上传后：
  ✅ 文档已支持检索
  📝 AI摘要持续进行中 50%     ← 用百分比，不用 x/y
  
KB 文档列表页：
  📄 [文档概览]     [重新生成摘要]
  摘要：涵盖中医经络理论、刮痧疗法...
  状态：✅ 已完成 / ⏳ 50%
```

#### 摘要 Prompt 设计

```
单 batch 摘要（每个 batch 调用）:
  Prompt: "用150字以内概括以下文本的核心主题、关键信息和重要细节。"
  temperature: 0.2（偏确定性，摘要不需要创造性）
  max_tokens: 200

合并摘要（最终调用）:
  Prompt: "以下是一份文档各部分的摘要，请合并为一段150字以内的文档概要，
          涵盖主要主题、内容范围和关键亮点。"
  temperature: 0.2
  max_tokens: 250
```

> **batch 摘要长度**：150 字（不是 30 字），因为一个 batch ~2000 字，
> 1/13 的压缩率比较合适，既不会丢失太多信息，也不会太冗长。

## 四、Token 计数器精细化

### 4.1 context_window 定义

**核心原则**：环形进度只跟踪**输入 token**（prompt_tokens），因为输入窗口满了 = 上下文耗尽 = 需要新会话/压缩。输出 token 不挤占输入窗口。

```
┌──────────┬────────────────┬─────────────────────────────────────┐
│ 模式     │ 输入窗口       │ 来源                                │
├──────────┼────────────────┼─────────────────────────────────────┤
│ 在线     │ 模型动态       │ MODEL_CAPABILITIES[name].context    │
│ (GLM-5.1)│ 200K           │ 字典取值                            │
├──────────┼────────────────┼─────────────────────────────────────┤
│ 离线     │ 8K (num_ctx)   │ 固定值（Qwen3.5-4B num_ctx=8192）  │
│ (本地)   │                │ 输入满了 → 提示新建会话              │
└──────────┴────────────────┴─────────────────────────────────────┘

环形进度 = 累计 prompt_tokens / 输入窗口
  - 在线：prompt_tokens / 200K
  - 离线：prompt_tokens / 8K
  - 80% → ⚠️ 即将满
  - 95% → 🔴 触发自动压缩（在线）/ 提示新建会话（离线）
```

### 4.2 数据采集

```
在线模式（CloudEngine SSE 最后一个 chunk）:
  OpenAI SDK streaming 最终帧:
    usage.prompt_tokens      → 输入 token（含 system prompt + 工具 + 历史）
    usage.completion_tokens  → 输出 token（含 reasoning）
    usage.completion_tokens_details.reasoning_tokens → 推理 token

离线模式（Ollama /api/chat 最终帧）:
    prompt_eval_count  → 输入 token
    eval_count         → 输出 token
    （无 reasoning 概念）
```

### 4.3 数据存储 — chat.json

每条消息增加 `token_stats` 字段：

```json
{
  "role": "assistant",
  "content": "...",
  "timestamp": "2026-06-07T18:36:07",
  "token_stats": {
    "input_tokens": 8523,
    "output_tokens": 421,
    "reasoning_tokens": 3200
  }
}
```

- 在线模式三个字段都填
- 离线模式 `reasoning_tokens` 填 0
- 用户消息的 `token_stats` 只填 `input_tokens`（估算：len(content)/1.5）

### 4.4 前端展示

```
┌─────────────────────────────────────────┐
│  上下文环形计数器                          │
│                                         │
│  主显示（环形内的文字）：                   │
│    在线：15K / 200K                      │
│    离线：6K / 8K                         │
│                                         │
│  环形进度：                               │
│    = 累计 prompt_tokens / 输入窗口        │
│    （只看输入，输出不挤占环形）             │
│                                         │
│  hover/tooltip 明细（在线模式）：          │
│  ┌──────────────────────────────┐       │
│  │ 本次会话 Token 用量           │       │
│  │ 输入    12.5K (历史+工具)     │       │
```

### 5.2 优先级设计

```
┌─────────────────────────────────────────────────────────────┐
│                 LLMScheduler（统一 LLM 调度器）               │
│                                                             │
│  消费者队列（按优先级）:                                       │
│    P0 — Chat（用户实时对话）     → 立即执行，抢占式            │
│    P1 — 纪要（润色/总结）        → 用户触发时等同 P0          │
│    P2 — KB Summary（文档摘要）   → 空闲时执行，可被 P0/P1 抢占 │
│                                                             │
│  抢占规则：                                                   │
│    1. 当前无任务 → 按优先级取最高                              │
│    2. P0/P1 请求进来 → 等当前 LLM 调用完成后执行              │
│       （不能中断正在进行的生成，需要调研 Ollama 中断机制）     │
│    3. P0/P1 完成 → 恢复被抢占的 P2 任务                       │
│    4. 同优先级 FIFO                                           │
│                                                             │
│  在线模式 vs 离线模式：                                       │
│    在线：Chat 走云端，本地 LLM 只服务 P1/P2                   │
│          → 纪要和 KB 摘要可以排队执行（不冲突）               │
│    离线：Chat 抢本地 LLM，P1/P2 在后面等                     │
│          → 用户发消息时 KB/纪要暂停，回复后自动继续            │
│                                                             │
│  纪要前端提示：                                               │
│    "所有处理均在本地完成，数据不会上传到云端"                   │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 关键技术问题：Ollama 中断机制

> **需要调研**：Ollama 用户可以在前端手动中断模型响应，
> 说明存在某种中断 API 或 SSE 连接断开机制。
> 需要确认：
> 1. Ollama 是否有显式的 cancel/abort API？
> 2. 断开 SSE 连接后 Ollama 是否立即释放资源？
> 3. 如果可以中断，调度器可以做到真正的抢占而非"等完成"

### 5.4 与现有架构的关系

```
现状：
  GenerateQueue → 只服务 Chat

Patch3 目标：
  LLMScheduler（替代 GenerateQueue 的角色）
    ├─ P0 队列：Chat 请求
    ├─ P1 队列：纪要 润色/总结
    └─ P2 队列：KB Summary batches
```

**分步实施**：

- **Patch3 第一批**：保持 GenerateQueue 给 Chat 用，SummaryScheduler 作为独立调度器监听 GenerateQueue 空闲状态
- **Patch3 第三批**：统一为 LLMScheduler，加入纪要（P1），形成完整三级调度

### 5.5 纪要模块补充

纪要消费 LLM 的两个位置：
1. **润色**：用户手动触发，对转写文本进行语言优化
2. **纪要总结**：用户手动触发，生成会议纪要

两者都是用户主动操作，触发时应该等同 P0（用户在等待结果）。
但如果纪要总结特别耗时（长录音），也需要考虑断点续传机制（当前未实现，后续可加）。

## 七、已确认事项

| # | 问题 | 决定 |
|---|------|------|
| A | 离线 context_window 显示方式 | **环形只跟踪输入 token / 8K**，满了提示新建会话。输出不挤占环形 |
| B | 摘要粒度 | **批量采样摘要（方案 δ）**：chunk 合并为 batch ~2000 字，逐 batch 摘要后合并为文档级 summary |
| C | 摘要 Prompt 语言 | **中文**，batch 摘要 150 字，合并摘要 150 字 |
| D | KB 权限设置入口 | **设置页**，数据发送策略的子选项 |
| E | 摘要走哪个 LLM | **永远走本地 LLM**，不上传到云端（隐私原则） |
| F | 纪要摘要走哪 | **永远走本地 LLM**，前端提示"所有处理均在本地完成" |
| G | 纪要优先级 | **P1**（用户手动触发时等同 P0），KB 摘要是 P2 |
| H | 多文档摘要顺序 | **文档级 FIFO**（一个文档做完再下一个） |
| I | 摘要进度显示 | **百分比**（不用 x/y 格式） |
| J | 断点续传 | batch 级别断点续传，每个 batch 完成后保存，下次从断点继续 |
| K | batch 温度 | **0.2**（偏确定性，摘要不需要创造性） |
