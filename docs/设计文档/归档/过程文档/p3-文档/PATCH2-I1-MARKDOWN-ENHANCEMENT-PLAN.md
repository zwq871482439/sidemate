## 2. 方案评估

### 方案 A：继续手写正则增强 md()

| 维度 | 评估 |
|------|------|
| **开发量** | 中（表格 ~50行，任务列表 ~20行，脚注 ~40行，图片/删除线/HR ~30行） |
| **风险** | 高 — 正则容易出边界 bug，表格+嵌套列表的正则极难写对 |
| **流式兼容** | 需要额外处理未闭合表格 |
| **维护成本** | 高 — 正则堆叠后难以维护 |
| **扩展性** | 差 — 每加一种语法都要改核心函数 |

### 方案 B：引入 marked.js（轻量 Markdown 库）

| 维度 | 评估 |
|------|------|
| **体积** | ~40KB（min+gzip ~12KB），已有 KaTeX 30KB 先例 |
| **开发量** | 小 — 替换核心，配置 extensions |
| **流式兼容** | marked 支持 async + 自定义 tokenizer |
| **维护成本** | 低 — 社区维护 |
| **扩展性** | 好 — 插件体系，支持 GFM 表格/任务列表 |

### 方案 C：引入 markdown-it（更重但功能全）

| 维度 | 评估 |
|------|------|
| **体积** | ~60KB |
| **功能** | 最全，插件生态最好 |
| **风险** | 中 — 迁移成本稍高 |

### 推荐：方案 B（marked.js）

理由：
1. **最小改动**：只需替换 `md()` 内部实现，外部调用不变
2. **体积可控**：12KB gzip，对离线桌面应用影响极小
3. **原生支持 GFM**：表格、任务列表、删除线开箱即用
4. **流式友好**：可通过自定义 renderer 处理流式场景
5. **已引入第三方库先例**：KaTeX、highlight.js 已在 vendor 中

## 4. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| marked 升级导致行为变化 | 低 — 锁定版本 | vendor 目录固定版本 |
| 流式中表格未闭合导致渲染错乱 | 中 | 流式模式下对未闭合 `<table>` 做兜底 |
| 脚注在对话场景不常用 | 低 | 优先级可降低，先交付表格+任务列表 |
| 现有对话消息渲染回归 | 高 | md() 外部接口不变，逐条验证 |

---

## 5. 交付标准

1. **表格渲染**：GFM 表格正确显示，含对齐语法（`:---`, `:---:`, `---:`）
2. **任务列表**：`- [ ]` 和 `- [x]` 渲染为 checkbox
3. **脚注**：`[^1]` + `[^1]: text` 渲染为上标链接 + 底部注释
4. **图片**：`![](url)` 渲染为 `<img>`，可点击放大
5. **删除线**：`~~text~~` 渲染为 `<del>`
6. **水平线**：`---` 渲染为 `<hr>`
7. **流式兼容**：流式输出时不会因语法未闭合而炸渲染
8. **回归无异常**：现有代码块、LaTeX、列表、引用等渲染不受影响
