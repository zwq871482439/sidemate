## 三、模式系统重构（2026-06-18 新增）

### 3.1 背景

当前模式系统混乱：
- **Chat Tab**：本地 / 云端 两档切换
- **文库 Tab**：独立对话窗口，带"云端对比"隐藏开关
- **痛点**：用户要在两个 Tab 之间切换才能用"本地安全+云端补充"的对比模式；文库 Tab 职责不清（既管上传又管对话）

### 3.2 目标架构（⚠️ 三主模式 + 隐身协作双子类型）

> 🚨 关键决策链（2026-06-19）：
> - 21:13 三种模式**长期并存**，非替代关系
> - 21:23 定名"隐身协作"
> - 21:39 **隐身协作拆双子类型**（用户决策：3主+子 比 4主 不晕）

```
┌─ 模式选择（Chat Tab 顶部）─────────────────┐
│  🏠 本地模式                                │  纯本地，完全不上云（P4）
│  ☁️ 在线模式                                │  纯云端 + 令牌系统（P4+P5）
│  🛡️ 隐身协作                                │  本地+云端协作（P6）
│     ┌─────────────────────────────────┐    │
│     │ ◉ 📊 隔离对比（默认）             │    │  100% 不上云
│     │ ○ 🤝 智能代理                    │    │  脱敏后部分上云
│     └─────────────────────────────────┘    │
└────────────────────────────────────────────┘
```

**UX 设计**：
- 模式选择器主体 3 个选项（不晕）
- 选"🛡️ 隐身协作"后**展开 2 个 radio 子类型**（不强制选，默认隔离对比）
- 切换子类型在 Chat Tab 内即可，无需回到顶部模式选择器

**Chat Tab 主体按模式自动切换后端 pipeline**：

| 主模式 | 子类型 | 后端 pipeline | 隐私机制 | KB 上云 | 上线版本 |
|--------|--------|--------------|---------|---------|---------|
| 🏠 本地 | — | `local_pipeline` | 完全不上云 | ❌ | P4 |
| ☁️ 在线 | — | `cloud_pipeline` | **令牌系统** | ⚠️ 受控 | P4+P5 |
| 🛡️ 隐身协作 | 📊 隔离对比 | `compare_pipeline`（已有）| **100% 不上云** | ❌ | **P6** |
| 🛡️ 隐身协作 | 🤝 智能代理 | `hybrid_pipeline`（新）| **脱敏草稿+三道防线** | ⚠️ 脱敏后 | **P6** |

### 3.2.1 双子类型对比（关键决策）

| 维度 | 📊 隔离对比 | 🤝 智能代理 |
|------|-----------|-----------|
| **数据流向** | 本地答 + 云端答（各自独立）| 云端指挥 + 本地代理 |
| **KB 暴露** | 100% 不去云端 | 脱敏后部分上云 |
| **云端能力** | 只能用通用知识 | 可通过工具"借用"本地知识 |
| **答案质量** | 中（云端没 KB 加持）| 高（云端有脱敏 KB 摘要）|
| **实现难度** | 低（照搬 Patch3 compare_pipeline）| 高（新架构）|
| **风险** | 极低 | 中（需打磨脱敏质量）|
| **适用人群** | 极度保守派 | 理性平衡派 |

**子类型命名理由**（用户决策方案 A "按数据流向"）：
- **隔离对比**：数据完全隔离，双轨对比（强调"隔离"=安全）
- **智能代理**：云端智能指挥本地代理（强调"代理"=分工）

### 3.3 知识库 Tab 改造（原"文库 Tab"）

**⚠️ 名字变更**：文库 → **知识库**（更准确，反映"档案管理"定位）

**改造前**：文库 Tab = 档案管理 + 对话（混在一起，职责不清）
**改造后**：知识库 Tab = **纯档案管理**

知识库 Tab 职责：
- 文档上传/删除/批量操作
- 自动打标 + 人工修正
- Tag 聚类展示
- 检索诊断面板（见下方说明）
- 🔒 隐私标记（私密文档）
- 知识自动关联（P6+ 扩展，待定）

**"检索诊断面板"说明**（替代原"检索测试 playground"）：
- 命名理由：playground 太娱乐化，"诊断"更符合 KB 管理的专业定位
- 功能：用户输入 query → 显示命中的 chunk（文件名+章节+分数+命中段落预览）
- 用途：验证文档是否被打标正确、检索是否命中预期、调试 chunk 切分质量
- 面向场景：高级用户/管理员调优 KB，不是日常对话

**对话功能拆分迁出**（⚠️ 修正：不是全部迁隐身协作）：
- 原文库 Tab 的**本地问答** → 迁到 Chat Tab **本地模式下的 action 按钮**（`action_mode = 'kb_qa'`）
  - 理由：本地问答本来就属于本地模式，不该单独开模式
  - 实现：本地模式加一个"📖 查文库"action 切换
- 原文库 Tab 的**云端对比** → 迁到 Chat Tab 的"🛡️ 隐身协作模式"
  - 理由：云端对比的本质就是"本地+云端协作"，正好对应隐身协作
- 知识库 Tab **不再有任何对话功能**

### 3.4 用户心智模型简化

**改造前**（用户困惑）：
- "我要查文库应该去哪个 Tab？" → 文库 Tab
- "我要对比本地和云端应该去哪？" → 也去文库 Tab，但要打开隐藏开关
- "本地模式怎么用文库？" → Chat Tab 本地模式会自动检索

**改造后**（清晰统一）：
- 所有对话都在 Chat Tab（按模式分流）
- 想要什么效果选对应模式即可
- 知识库 Tab 只管"我有哪些文档"（纯档案管理）

### 3.5 隐身协作模式（✅ 定名 2026-06-19 21:23，双子类型 21:39）

> 🎯 **最终命名：隐身协作**（4字 + 强调隐私 + 暗示云端协作）
> 命名理由："隐身"传达"云端看不见原文"，"协作"传达"本地+云端一起干"

> 💡 **双子类型架构**（用户决策 21:39）：
> - 主模式只有 3 个（不晕）
> - 隐身协作展开 2 个子类型 radio（默认隔离对比）
> - 覆盖用户信任光谱：极度保守（隔离对比）/ 理性平衡（智能代理）

**子类型 A：📊 隔离对比**（照搬 Patch3 compare_pipeline）
- 数据流向：本地答 + 云端答（各自独立）
- KB 暴露：100% 不去云端
- 云端能力：只能用通用知识
- 答案质量：中（云端没 KB 加持）
- 实现难度：低（已有）
- 适用：极度保守派

**子类型 B：🤝 智能代理**（新架构，见 3.6 本地工具代理）
- 数据流向：云端指挥 + 本地代理
- KB 暴露：脱敏后部分上云
- 云端能力：可通过工具"借用"本地知识
- 答案质量：高（云端有脱敏 KB 摘要）
- 实现难度：高（新架构）
- 适用：理性平衡派

**核心痛点**（用户深度思考后定调）：
> 本质上是不想让大模型看到我本地知识库里有什么东西。
> 宝贵文档喂给大模型 = 免费训练材料 + 丢失风险 + 泄露风险。

**旧对比模式的本质缺陷**：
- 本地和云端**都看 KB**（隐私问题）
- 令牌系统只是"渐进暴露"，云端调一次 search_kb 内容还是出去了

**隐身协作模式架构**（本地代理 + 脱敏草稿）：

```
用户问题："中医怎么调理脾胃"
   ↓
[本地 LLM 做智能路由 + 脱敏代理]
   ├─ 公开知识问题 ─────────────────→ 云端回答（不碰 KB）
   │  例："什么是脾胃"
   │
   ├─ 私有知识问题 ──→ 本地 LLM 检索 KB → 本地生成答案（不上传）
   │  例："我的养生笔记里怎么说的"
   │
   └─ 混合问题 ──→ 本地 LLM 用 KB 生成"脱敏草稿" → 云端润色
      例："根据我的笔记 + 通用知识，分析脾胃调理"
       (云端只看草稿，不看原始 chunk)
```

**关键创新：脱敏草稿（Sanitized Draft）**

```
原始 chunk: "张三的体检报告显示肝功能异常 ALT 86"
   ↓ 本地 LLM 脱敏
脱敏草稿: "体检报告显示某指标偏高，需要调理肝脏"
   ↓ 发给云端
云端润色: "肝功能指标偏高建议从饮食、作息、中药三方面调理..."
   ↓ 本地合成
最终答案: 云端润色 + 本地从 KB 提取的个性化建议
```

**对比新旧方案**：

| 维度 | 旧对比模式 | 新隐身协作 |
|------|-----------|-----------|
| 本地 LLM 看 KB | ✅ | ✅ |
| 云端看 KB 原文 | ❌（隐私问题）| ✅ 永远看不到 |
| 云端看脱敏草稿 | — | ✅（可选，用户控制）|
| 云端训练风险 | 高 | 低 |
| 本地 LLM 角色 | 平等贡献者 | **守门人 + 代理** |

### 3.6 进阶架构：本地工具代理（云端指挥 4B 干活）

> 💡 用户创新想法（2026-06-19 21:23）：
> 虽然 4B 干不了啥，但是大模型是不是可以指挥 4B 干点啥？
> 不用这么死板搞结构化，但担心大模型指挥 4B 乱干活，产出还是出去了。

**核心机制**：云端 LLM 通过 `local_assistant` 工具调用 4B，4B 是云端的"本地手"。

**架构**：
```
云端 LLM（决策者）
   ↓ 调用 local_assistant 工具
4B（执行者，戴"脱敏手套"）
   ↓ 检索 KB + 结构化任务
脱敏层（三道防线）
   ↓ 过滤后
返回云端（只看脱敏摘要）
```

**允许的任务白名单**（4B 拒绝任意开放指令）：

| 任务 | 4B 干啥 | 输出 | 示例 |
|------|--------|------|------|
| `summarize(topic)` | 检索 + 总结某主题 | 200 字摘要 | "脾胃调理的中医方法" |
| `extract_keywords(topic)` | 检索 + 提取关键词 | 5-10 个词 | ["饮食", "作息", "情志"] |
| `compare(a, b)` | 对比两个观点 | 结构化对比 | "学派 A vs 学派 B" |
| `count(condition)` | 统计符合条件的数量 | 数字 | "提到经络的文档数" |

**禁止的任务**（4B 拒绝执行）：
- ❌ "输出原文" / "逐字复述" / "翻译全文" / 任何开放性指令

**三道脱敏防线**（解决"产出出去"担忧）：

```
4B 输出
  ↓
① 规则过滤：去人名/数字/特定术语（正则）
  ↓
② 相似度检测：输出 vs 原文 chunk，>70% 相似 → 整段作废重做
  ↓
③ 长度限制：单次输出 ≤ 300 字
  ↓
返回云端（安全）
```

**关键设计**：第 ② 层相似度检测是杀手锏——即使 4B 被骗偷懒复述原文，相似度 >70% 直接拦截，整段作废。

**方案对比**：

| 方案 | 4B 角色 | 灵活性 | 安全性 | 复杂度 |
|------|--------|--------|--------|--------|
| 死板结构化（3.5 基础版）| 路由 + 脱敏 | 低 | 高 | 低 |
| **本地工具代理**（3.6 进阶版）| 云端的本地工具 | **高** | **高（三道防线）** | 中 |
| 完全放开 | 跟云端对话 | 最高 | 低 | — |

**甜蜜点**：本地工具代理 = 享受云端决策 + 三道防线兜底。

**工作流示例**：
```
用户：帮我分析下中医调理脾胃的方法

云端（DeepSeek）：
  "这需要本地知识，调用 local_assistant"
  → local_assistant.summarize("脾胃调理", max_length=200)

4B 本地执行：
  - 检索 KB → 3 个相关 chunk
  - 按模板总结："中医调理脾胃注重饮食、作息、情志..."
  - 输出 180 字摘要

脱敏层：
  - 规则：去掉"张三"→"某患者"
  - 相似度：摘要 vs 原文 = 45%（通过，<70%）
  - 长度：180 字（通过，<300）

返回云端："中医调理脾胃注重..."（脱敏后）

云端：基于脱敏摘要 + 通用知识生成完整回答
```

**隐藏价值**：
1. 4B 不需要"思考"，只执行结构化任务（符合能力边界）
2. think 可保持关闭（走模板不走推理链）
3. 任务可审计（每次调用记日志，用户可见）
4. 扩展性强（未来可加 translate_summary / fact_check 等）

```
│                                              │
│  ☁️ 云端助手：（收到草稿）                   │
```

**UI 设计原则**：

- **单列 + 时间线动画**（小人物 + 气泡表达流程）
- **可见性**：用户能清楚看到"本地在干啥" + "云端在干啥" + "信息从哪来"
- **本地 think 关闭**：4B 模型开 think 出问题，用结构化流程替代

### 3.7 本地 4B 模型的能力边界（关键约束）

**现实**：4B 模型太弱，开 think 会出各种问题。

**应对策略**：
- 不依赖本地 LLM 的"自由思考"
- 用**结构化流程**（Pipeline）强制执行：
  1. 路由分类（公开/私有/混合）→ 简单 prompt
  2. KB 检索 → 工具调用（不需要思考）
  3. 脱敏草稿生成 → 固定模板 + 关键信息提取
  4. 最终合成 → 固定模板 + 信息融合

**复杂回答能力不足时**：
- 答不出的私有问题 → 诚实告知"本地能力有限，建议切到在线模式"
- 混合问题的合成 → 如果本地合成质量差，可以只展示脱敏草稿 + 云端润色（不做深度融合）

### 3.8 实施复杂度评估

| 模块 | 改动 | 复杂度 |
|------|------|--------|
| 模式选择 UI | 加"🛡️ 隐身协作模式"选项 | 低 |
| **hybrid_pipeline**（新） | 路由 → 脱敏草稿 → 云端润色 → 本地合成 | **高** |

### 5.1 核心理念

**"ClearBox 明盒"** = 对抗 AI 黑盒的产品哲学

```
│  └─ Agent 状态实时广播                   │

└──────────────────────────────────────────┘
```

## 六、KB Tag 智能归并 + 分组显示（2026-06-21 从 P5 推迟）

### 6.1 背景

当前自动打标生成的 tag 数量爆炸：12 篇中医文档能撒出 40+ tag，每篇独立生成不参考全局，结果就是同义词满天飞（中医基础/中医理论/中医健康/中医养生/中医秘传 5 个意思接近的 tag）。

### 6.2 设计目标

- 不动 LLM prompt（4B 改不动 prompt 也救不了）
- **归并算法**做通用化（不能只针对中医，下一轮测试可能是别的主题）
- **分组 UI**：从平铺改为按 tag 聚合
  ```
  -- 中医（5篇）
     ---- 中医基础（3篇）
     ---- 中医养生（2篇）
  -- 流派传承（4篇）
     ---- 医经学派（1篇）
  ```

### 6.3 归并算法候选方案

#### 方案 A：硬编码同义词字典 ❌
- 维护成本高，不通用

#### 方案 B：前缀匹配归并 ⭐ 候选
- 「中医基础」+「中医养生」+「中医理论」→ 都以「中医」开头，归到「中医」父类
- 规则：长度 ≥ 4 字的 tag，按前 2 字归父类
- 优点：完全无 LLM 依赖，毫秒级
- 缺点：可能误归并（"AI 编程" 和 "AI 写作" 父类不同但前 2 字相同）

#### 方案 C：Embedding 相似度归并 ⭐ 候选
- 用 bge-m3 给所有 tag 算向量，相似度 >0.85 的归并到第一个
- 优点：通用、语义级
- 缺点：需要加载 embedder（~2GB），启动慢

#### 方案 D：B+C 混合 ⭐ 候选（推荐）
- 先做 B（前缀归并），快速粗筛
- B 之后剩下的 tag 再过 C（embedding 细筛）
- 平衡速度和准确度

### 6.4 待决策

- [ ] 用户能否手动调整归并结果？
- [ ] tag 在 Chat 模式下的注入策略（全量/按需）？
